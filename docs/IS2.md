## Root binding

The source-owned Windows adapter opens and hashes the exact selected executable,
keeps that file open without write/delete sharing through process creation, calls
ordinary CreateProcessW with no shell or elevation override, and validates the
created process's image file identity and creation FILETIME using its returned
process handle. It emits one bounded stderr frame before resuming the suspended
child. That frame binds the manager operation, fresh 256-bit token, launch epoch,
import digest/size and both Windows process generations. The token is not placed
in the child's environment or arguments. The private request is removed at cleanup.

The manager packages the adapter as an immutable optional Software artifact and
verifies it before passing it to the installer supervisor. Legacy software and
schema-2 records remain readable. A package lacking the adapter retains the exact
previous adapter when available. No frontend action accepts an adapter path or
command. This artifact is installer-only and does not change any VST host/native
product artifact. Direct MSI remains the existing separate route; it makes no new
IS2 EXE-root claim.

Root authority is independent of Wine's direct-loader creation logging. An
unpredictable-token frame is accepted only in the expected stderr stream and
launch epoch, once, with the exact operation/artifact identity. Missing, malformed,
conflicting or duplicate records remain unavailable. Windows IDs never become
Linux ownership. Cgroup/PID-start custody, reaping and cancellation stay with IS1.

This protocol is diagnostic custody among project-owned observations within the
existing same-user Wine environment, not a security boundary against malicious
same-user code. It grants no permission to signal a process. All actual termination
still belongs to the exact cgroup or source-owned fixture's retained process handle.

## Presence and close records

A bounded strict grammar classifies observed PowerShell/CIM operations; it does
not execute, rewrite or emulate a script. Private records retain exact command
SHA-256, predicate SHA-256, request timestamp, helper process ordinal/generation,
caller relationship, helper exit domain/status and requery relationship. Only a
fully matching grammar grants a closed operation classification. Unrecognized
scripts remain unknown; names alone grant no semantics.

A helper exit zero is never a matched-object count, successful close, successful
recheck or proof of interpreter capability. Those fields remain explicitly
unavailable without exact object/result observation. Pre-root and unmatched helper
rows are labelled unbound. Source-owned API fixture measurements independently
exercise exact target generation, cooperative close, retained presence, stale
objects, self-detection, unrelated processes, cancellation and cleanup; fixture
oracles are not admitted as vendor evidence.

Public manager readback validates operation/schema/limits and exposes launch-root
availability and the distinction between observed requests and unavailable
results. It preserves outer exit, durable installation, prior failure and cleanup
as separate fields. No ordinary admission or audio callback is involved.

## Scope and limitations

The production observer records the established script-based mechanism. It is not
a universal Win32 API hook: window, mutex, registry, service and file-lock matches
without exact observations remain unknown. A source-owned API oracle measures
the generated close cases independently; it cannot authorize vendor attribution.
In particular, helper success, application-file absence and successful cleanup do
not establish a false positive, successful close or healthy installation.

The generated Windows fixtures use owned process handles, creation time and the
exact source-owned window owner. A class check narrows that already-owned
fixture's windows; class names never grant process ownership. A same-name peer is
preserved through the target close and then retired separately by its retained
fixture handle. Actual numeric PID recycling is not forced: deterministic trace
reuse and a mismatched expected process generation prove refusal.

Working-directory/environment comparisons normalize only the two exact disposable
attempt roots. Both ordinary and requireAdministrator payloads have equal direct
and adapted results/elevation posture under the pinned runner. No host privilege
is granted. Native Windows tests additionally verify copied input, a hardlink
alias, unrelated same-basename bytes, wrappers before the adapter, ordinary child
wrappers, exit propagation and a truncated request.
