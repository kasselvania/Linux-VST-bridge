# User control over executables and Wine

Research and proposal, 2026-10-14. Source audit only; no installation, runtime, prefix, activation or device changes. Test69 and the retained SteamOS/CachyOS installations remain untouched.

**Recommendation: give users an editable working setup, with the manager remembering what they selected and helping them maintain it.** A changed hash should lead to “Use this version,” not require maintainer permission. Keep exact identities for history and reliable launches; remove product/build whitelists and installer-history requirements where they substitute for the user's explicit selection.

The user's requested control conflicts with the old workspace restriction against executable selection. The proposed flow replaces that restriction while retaining immutable history. The native architecture already permits unfamiliar runners and local overrides; it explicitly admits that the complete workflow is unimplemented. See `docs/WINDOWS_DAW_WORKSPACES.md:38–61` and `docs/ARCHITECTURE.md:1295–1307,1327–1332,1355–1371`.

## What the code actually permits and blocks

| Area | Current implementation and implication |
| --- | --- |
| Product authenticity | `bridge-manager/src/portable_package.rs:95–106` verifies the product release signature. Keep this: authenticating the manager's delivery does not authorize deciding which user executable may run. Signing keys need no change. |
| Executable identity | `bridge-manager/src/lib.rs:314–322` rejects changed artifact bytes. This detects that an old record no longer describes a file; it supplies no reason to forbid recording and running the user's new selection. |
| Native setup maintenance | Imported installers are retained by content, without an enumerated installer digest requirement (`bridge-manager/src/installer_import.rs:200–265`). Any imported installer is offered for an existing setup (`bridge-manager/src/operator_cli/environment_install.rs:246–262`); the GUI exposes this chooser (`manager-ui/src/library.rs:954–972`). Preserve this useful mechanism. |
| Vendor applications | Generic `ApplicationId::Selected` already exists (`bridge-manager/src/vendor_application.rs:23–25`). However, choices require a completed managed installation, uninstall-registration observations and matching changed-file observations (`bridge-manager/src/vendor_cli/selection.rs:25–108`). A portable executable, omitted installer registration or externally updated executable has no ordinary user-selection/adoption action. The older document's closed-ASC premise is stale; the remaining receipt requirement is the real restriction. |
| Runtime choice | The GUI offers recorded installed runtimes (`manager-ui/src/library.rs:916–938`). Sources include delivery records, registered environments and retained transitions (`bridge-manager/src/operator_cli/environment_runtime.rs:57–72`); this is broader than one shipped runner. But there is no generic import action in `bridge-manager/src/operator_model.rs:73–296`. Worse, switching requires the **old** runner to pass byte verification before selecting the replacement (`bridge-manager/src/operator_cli/environment_runtime.rs:93–118`). That unnecessarily blocks recovery from an edited or damaged old runner. |
| Windows DAW workspace | FL discovery accepts only `FL64.exe`/`FL Studio.exe` under Image-Line and requires exactly one match (`bridge-manager/src/daw_workspace.rs:1603–1658`). Installation requires prior uninstall and rejects an unmanaged image (`:1437–1458`). Serum selection requires one hardcoded digest and release (`:1785–1788`). These are actual permission restrictions, confined to this lane; replace them with general selection and update operations. |
| Wine controls | Native local settings contain graphics and accessibility choices only (`bridge-manager/src/operator_model.rs:12–32`); launch code constructs specific DLL overrides internally (`bridge-manager/runtime/session.py:249–267`). There is no general Wine configuration, DLL-order editor or runtime-import control in the action model. |

The managed runtime verifier also rejects changed files **and added files anywhere in its recorded tree** (`bridge-manager/src/runtime_delivery.rs:323–372`). This is reasonable for a retained distribution image, but unsuitable as the definition of a user's editable Wine suite. A local runner must have its own editable working location and adoptable revisions.

Native refresh already discovers and connects missing plug-ins while preserving available publications (`bridge-manager/src/operator_cli/environment_refresh.rs:135–182`). This is useful groundwork, not a general executable-adoption operation. Saved-state code already separates exact recovery from loading state into the selected successor (`native-vst3-proxy/backend/src/state.rs:528–542`); changing a module digest need not invalidate a musician's project.

## A simpler musician flow

Each setup gets **Programs**, **Wine settings**, and **Runtime** controls beside its normal Open/Install actions.

1. **Programs:** choose an executable, its working folder and optional arguments; launch once or remember it. Keep related resources in place. Existing detected applications are suggestions. “Run installer” targets this same setup, including updates over an existing installation; uninstall is required only when the vendor actually requires it.
2. **Wine settings:** open this runner's `winecfg`, expose DLL load order and useful launch options, and offer “Open setup folder.” Ordinary preferences, registry configuration, presets and content stay editable. Show when a per-launch override supersedes a Wine setting; reset removes that override. [Wine's current configuration manual](https://raw.githubusercontent.com/wine-mirror/wine/master/programs/winecfg/winecfg.man.in) documents DLL order, virtual desktop, drives, audio and per-application settings. [Proton's current options](https://github.com/ValveSoftware/Proton#runtime-config-options) document runtime environment overrides; applicability must follow the selected runner, not an evergreen checkbox list.
3. **Runtime:** choose a supplied runtime or a local coherent Wine/Proton distribution. Identify the adapter and missing capabilities directly. A user-maintained distribution remains selectable without a support-profile entry. Permit editing a local copy; never overwrite a shared delivered runtime behind other setups' selections.
4. **Changed files:** show “Program updated” or “Runtime changed,” with **Use this version** and **Choose another**. A supervised vendor update can authorize this refresh as part of the original action. External changes need one clear adoption action, not a new installation or repeated approvals. Record the selected bytes before launch and drop obsolete compatibility claims.

The minimal mechanisms are a selected program record, the existing environment/runner selection, and one refresh/adopt operation. Launch uses structured arguments, the selected runtime/prefix and the existing supervised process owner. An installer receipt is provenance when present, not a prerequisite for permission. Do not add another receipt database or an executable allowlist.

Retained history is immutable; the working setup is not. Keep an old runnable version only when its files/resources really remain available. A saved project records its producing version without choosing an executable. Switching back must never rewind newer projects, preferences or licensing state. Runtime changes can migrate a prefix, so retaining the old runner alone is not a full undo. Report that limitation when relevant; do not clone licensed machine identity to manufacture rollback. Keep exact process ownership and save opportunities; require closure of the affected setup when necessary, not unrelated environments by default.

## First implementation slice and observable acceptance

Have Sol implement **Choose program / Use changed version** in one existing native managed setup. Reuse the vendor-application supervisor but make user selection a first-class origin, independent of installer observations. Retain the current runtime and prefix. Add the chooser, remember the selection, and allow replacement bytes to be explicitly adopted. This delivers useful freedom before implementing the full Wine suite or generalizing the Windows DAW workspace.

Acceptance: through the installed GUI, select a lawful portable program that no installer registered, run/focus/close it, replace it with a distinguishable build, adopt that build and run it after restarting the manager. An unadopted change must never be labeled the old build. The original setup's plug-ins must still play and reopen saved state; projects, content and activation remain intact. This is future authorized validation, not work performed by this research.
