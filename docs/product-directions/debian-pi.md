# Debian and Raspberry Pi — research proposal, 2026-10-14

**Recommendation:** compare the existing standalone host with minimal native ARM REAPER as two ways to house the same playable Pi instrument. REAPER may reduce the amount of hosting/UI/state machinery we maintain; its CPU/memory advantage is unproved. Debian x86-64 packaging can progress independently. The appliance goal and delivered SteamOS/CachyOS beta remain unchanged.

**What actually worked.** Debian x86-64 and Raspberry Pi have different evidence:

- **Debian 13 amd64:** package installation/dependencies and real manager/frontend linking passed in containers. Manager startup reached its expected missing-installation refusal. Graphical launch, product adoption and DAW audio were not tested there. Target-specific Python 3.13 bytecode matters; Ubuntu 3.14 artifacts cannot simply be reused. See [BETA_PORTABILITY.md](../BETA_PORTABILITY.md), lines 30–56, and [paired startup results](../../evidence/beta-portability/paired-binary-startup-2026-09-28.json), lines 19–31.
- **Pi hardware:** Raspberry Pi 5 Model B Rev 1.1, 8 GB, Raspberry Pi OS Trixie/Debian 13.7, AArch64, ShieldXL CS4270 audio/UART MIDI, kernel `6.18.50+rpt-rpi-v8`, 4 KiB pages. Early source-owned instrument tests passed physical MIDI/audio/editor/state/restart. Box64/Wine failed with the earlier 16 KiB kernel; the ShieldXL driver was subsequently built and verified for the 4 KiB kernel. [Historical RPI0, lines 39–83](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI0_RESULT.md#L39-L83); [RPI1 machine, lines 238–240](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI1.md#L238-L240).
- **Commercial playing:** Pigments 7.0.1 first ran through Box64/Proton. Saved 45% volume returned in a fresh process; the owner played through OMX-27/ShieldXL and confirmed good sound. That run used JACK 512 at 48 kHz and a 2,048-frame bridge reserve: 42.7 ms before other latency. [Fresh-process result, lines 3–42](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI1_SAVED_STATE_FRESH_LAUNCH.md#L3-L42).
- **Later ARM runtime:** GE-Proton11-7 AArch64, UMU 1.4.4 and steamrt4-arm64 `4.0.20260914.260627` ran native ARM Wine infrastructure with FEX ARM64EC translating the x64 Windows host/plug-in. Pigments’ real editor, preset selection and fresh-process recall worked. Earlier migrated activation failed with a changed machine identity; operator activation resolved that specific state refusal. [Topology/results, lines 5–74](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L5-L74); [runtime, lines 694–717](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L694-L717).

**Editor-open performance was mixed.** Aioliane’s ordered closed/open/closed comparison averaged 16.66/26.37/12.45% whole-Pi CPU and added 512/1,536/0 missing frames. Heavier 24 AM failed even headless; profiling attributed about 90% of sampled user execution to translated Pigments processor code. GPU activity was observed, while VNC added CPU load. Faster bridge code cannot be assumed to remove that vendor workload. [Editor comparison, lines 893–925](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L893-L925); [heavy workload, lines 1084–1130](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L1084-L1130); [profile, lines 1704–1742](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L1704-L1742).

Serum 2.1.5 produced stereo audio and recalled volume, but its editor initially stayed white. DXVK rejected the Pi Vulkan capability; WineD3D plus software OpenGL made it visible. A later preset change kept the editor and processing alive, without a simultaneous sounding test. [Graphics result, lines 108–138](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/evidence/rpi2/serum2-instrument-onboarding.md#L108-L138); [preset result, lines 42–62](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/evidence/rpi2/serum2-preset-readback.md#L42-L62). These historical files survive in Git, not the current checkout.

**REAPER is a concrete host candidate.** Cockos currently offers REAPER 7.82 for Linux AArch64 and documents VST3, JACK and ALSA support. Use one monitored instrument track, MIDI input and stereo output. Download size and general efficiency claims do not establish its cost on this fixture. [Official download](https://www.reaper.fm/download.php), [technical capabilities](https://www.reaper.fm/about.php#technical).

REAPER needs our native AArch64 VST3 proxy; the standalone executable is not a loadable proxy. Applying Steinberg’s machine-named bundle rule gives `Contents/aarch64-linux` and an AArch64 `.so`. Current proxy CMake rejects ARM, and packaging builds the backend for x86-64. ARM proxy construction, publication and editor attachment are real prerequisite work. The Windows plug-in remains in the supervised Wine/FEX host. [VST3 bundle specification](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/Locations%2BFormat/Plugin%2BFormat.html), [CMake](../../CMakeLists.txt), lines 58–77, [package builder](../../tools/pkg0/assemble.py), lines 610–668.

**Reusable improvements.** Managed runtime acquisition, generic publication and current UI flow serve Debian. Test69 also removes optional editor construction from ordinary inspection, avoiding a graphics dependency during installation/update. [Current slice](../../CURRENT_SLICE.md), lines 24–29.

For Pi, the historical host polled thousands of times per second. Current notification/direct handoff is therefore a concrete opportunity, but its Rust Unix helper contains x86-64 assembly, while the retained Pi adapter explicitly uses protocol 12. Current production uses protocol 15. These are integration gaps, not proof that the legacy adapter cannot still run. The manager and `.deb` adapter also select x86-64/amd64. [Old polling, lines 184–216](https://github.com/kasselvania/Linux-VST-bridge/blob/82c459c27d4f3d01eef3a803b5b445aef172aeb5/docs/experiments/RPI2.md#L184-L216); [wait helper](../../tools/direct-audio-handoff/linux_wait.rs), lines 1–46; [Pi adapter](../../native-vst3-proxy/backend/src/rpi0.rs), lines 15–17; [architecture](../ARCHITECTURE.md), lines 1190–1263; [readiness](../../bridge-manager/src/readiness.rs), lines 803–811; [Debian adapter](../../tools/portable/deb.py), line 30.

The retained Serum default-state prewarm already removed the first-note gap in three short candidate runs, with exact restored state. It moved cold translation into startup; it did not improve sustained CPU capacity. Keep it opt-in. [PW1](../../evidence/pw1/serum-default-prewarm-2026-09-25.md), lines 42–103.

**Current external opportunities, checked October 14:** Debian lists 13.7 and supports both architectures. Raspberry Pi documents both 16 KiB and compatible 4 KiB kernels. FEX 2610 adds AVX-gather optimization and bounded disk-cache improvements. GE-Proton11-8, released October 13, updates FEX and enables disk caching by default. These justify a later pinned runtime comparison, not an automatic upgrade or a product performance claim. [Debian](https://www.debian.org/releases/trixie/), [Pi kernel documentation](https://www.raspberrypi.com/documentation/computers/linux_kernel.html), [FEX 2610](https://fex-emu.com/FEX-2610/), [GE-Proton11-8](https://github.com/GloriousEggroll/proton-ge-custom/releases/tag/GE-Proton11-8).

**First future implementation:** make a source-owned instrument play through the native ARM proxy in REAPER, with working editor/state/retirement. Reuse the shared engine; adapt its ARM boundary where required. Once both hosts use the same bridge/Windows-host revision, compare one previously playable commercial preset through standalone and REAPER. Hold plug-in bytes/state, runner, JACK 48 kHz/512, MIDI sequence, bridge delay, editor actions, cooling and power constant; disconnect remote screen streaming. Keep cold-start and warmed playing observations distinct. Preserve licensed state and the installed selection.

Use one short matched playing interval per host to measure host-only and whole-cohort CPU, memory, captured delivery gaps, physical MIDI-to-audio latency and felt response. Exercise editor open/close, a preset change, save/reopen, bounded host recovery and boot-to-play usability. Prefer whichever delivers dependable playing with acceptable resource cost and simpler operation/maintenance. Do not select REAPER merely from an idle reading. Separately, Debian’s first job is an ordinary graphical install-to-saved-project journey using its actual Python/library baseline.

**Musician acceptance:** install without Wine/compiler administration; select an instrument; play while its editor is open; change a preset/control; save, quit, reopen and reboot with the same sound; update and roll back without losing state. Pi additionally needs acceptable felt latency through ShieldXL and complete audio capture showing no missing sound during the chosen playing interval. A terminal counter or a rendered editor alone cannot establish that.
