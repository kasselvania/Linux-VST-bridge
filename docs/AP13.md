# AP13 — Delivery consistency and the installed lower-delay option

AP13 removes a demonstrated state-save barrier from active audio delivery and reduces routine supervisor CPU substantially. **512 frames per proxy remains the recommendation and installed setting.** The opt-in 256-frame setting works with a negotiated host maximum of 256, reports the correct lower latency, and passed one 45-second musical interval, but startup and editor-interval gaps prevent promotion. This is not a gap-free compatibility claim.

Issue: [#81](https://github.com/kasselvania/Linux-VST-bridge/issues/81). Prepared head `c05de4b2a405532b143e4124c97e36712597d678`; integrated AP12 main `c35839e7e812bfe94cd394c36d0a5e551bc3150f`. Tested implementation `16efd270ee7f00cbd365974d167bfe8448355acb`, tree `f55240eab87438da80ca98b6c6eb01068fb1d216`. Earlier AP8/AP9/AP12 source, results and failures remain intact. The numerical records below are in [evidence/AP13](../evidence/AP13/).

## Causal finding and repair

At 48 kHz, float32, host maximum/actual callback 512, internal chunks 256 and bridge delay 512, the first traced baseline LoFi gap was request **21607**, position **5530112**, first chunk of parent callback **10802**. It spent **105.569 ms queued** behind GetState, whose observed control interval was **111.936 ms**. Once dispatched, reply time was **3.325 ms**, including **3.0811 ms inside vendor process**. The next parent callback consumed the result after only about **10.871 ms**. A fast vendor process could not make up the preceding state barrier. This is observed queue/control contention, not 111 ms of plug-in DSP or proof that all historical outliers had this cause.

Follow-up owner timing measured LoFi's actual component and controller state capture: about **30–35 ms together**, with parameter metadata/value collection under 2 ms in those captures. Most observed controller/editor prelude work was microseconds; one repaired editor-opening capture spent **39.962 ms** servicing the editor before **33.702 ms** of opaque capture. Both opaque streams remain required. In the pinned SDK, a combined `SingleComponentEffect` can still implement distinct controller editor state; `controller_separate == false` does not justify dropping that stream.

Protocol minor **12** admits read-only GetState on the existing TCP/control mailbox, reserves its sequence, and lets ordered audio continue while the existing Windows UI owner captures state. The native worker incrementally consumes the correlated bounded response (at most 16 KiB per poll, at most the existing 1 MiB payload, 10-second control deadline). There is no new socket, broker or runtime. Restore and lifecycle controls retain exclusive ordering. Capture reports only a validated complete response; ordinary refusal preserves the previous snapshot and healthy session, while malformed responses, unsafe restore and endpoint loss remain terminal. A snapshot's audio position is an admission lower bound, not an invented sample-exact vendor snapshot timestamp.

The production SDK regression deliberately holds `getState` until four later SDK audio calls complete. The native full-callback regression holds and fragments a large state response while subsequent parent **512-frame callbacks** continue to deliver exact delayed samples. A serial save barrier fails this dependency; the repaired mailbox/queue path completes it. The SDK's declared UI/processing thread ownership is preserved: [IComponent](https://github.com/steinbergmedia/vst3_pluginterfaces/blob/4f547e8e102b47de4a8b8aaf343c73b700786372/vst/ivstcomponent.h), [IAudioProcessor](https://github.com/steinbergmedia/vst3_pluginterfaces/blob/4f547e8e102b47de4a8b8aaf343c73b700786372/vst/ivstaudioprocessor.h).

In the repaired commercial trace, editor-opening capture **10882** included the 39.962 + 33.702 ms owner work above, with no gap around that request. Other gaps remained at 9075 and 18204. The bounded Windows detailed history had already filled on earlier triggers, so per-audio-request QPC overlap at 10882 is **not retained**. The controlled SDK/transport test supplies direct concurrent-progress proof; this commercial observation supplies actual vendor behavior, not a second exact clock oracle. The first traced drag delivered no changed values, and its save shortcut did not write a project; those attempts are not counted as a successful gesture/save. Later untraced vendor edits and explicit File → Save did complete.

## Routine cost and callback storage

The AP9 identity-only census still visited every system process on every owner poll. `ProcessTracker` now performs the initial census once, then tracks PID/start-time identities and the children of every thread of each retained owned root. It retains reparented owned descendants and validates parent identity before/after enumeration. PID reuse cannot silently adopt a new process tree. Full positive cleanup, unexpected-exit detection and healthy siblings remain; the 50-ms polling interval is unchanged. Installers retain their existing supervision route.

Callback queues and output capacity are prefaulted while inactive. The first-use regression fills previously untouched parent-callback slots; later slot admission produces no minor faults. The strict assertion excludes the first call's host code/stack cold pages. This is a storage fault reduction, not an allocation-free claim for the non-real-time worker.

Matched, heavy-tracing-off 45-second runs used the original saved AP12 sound, same scene notes and recorded automation, closed editors, 48 kHz/float32, host 512 and bridge 512. CPU is percentage of **one core**, measured from `/proc` CPU ticks with PID/start-time matching:

| LoFi owner | 21.097% | 3.353% |

Durations were 45.029892224 and 45.027697845 seconds. The owner saving is about **81.0%**. Both runs had **zero gaps, missing or expired frames** in both devices. That interval demonstrates a CPU saving; it cannot establish a gap-rate improvement where the baseline already had zero gaps. No global priority, CPU weight, power, runtime or buffer increase was made by this implementation. The CPUWeight drop-in was observed unset before these comparisons. ## Installed selection and timing contract

The installed manager command is `linux-vst-bridge set-delay CLASS_ID 256` (or `512`). It selects versioned performance data separately from vendor state and class identity. All bridged audio instances must be closed; the environment keeper may remain. Existing registrations default to 512. The live installed route refused both changes while audio leases existed, accepted 256 after closure, and was restored to 512 afterward.

The versioned binding conveys the selected delay. Setup validates **delay >= actual negotiated host maximum**; 256 with host maximum 512 or 257 is refused before activation. Legacy bindings retain 512 behavior. Recovery refuses an incompatible changed preference until normal reopen. No callback waits, spinning, filesystem operations, serialization, allocation or UI work were added. Input samples, ordered events/automation, returned-event payload lifetime, late required note-offs and presentation offsets retain their production paths.

| Tested host maximum / actual callback | Internal maximum | Added per proxy | Chain bridge + vendor | Bitwig display |
| --- | --- | --- | --- | --- |
| 512 / 512 | 256 | 512 | 1024 + 240 = **1264 frames / 26.333 ms** | 26.3 ms |
| 256 / 256 | 256 | 512 | 1024 + 240 = **1264 frames / 26.333 ms** | Same reported pipeline |
| 256 / 256 | 256 | 256 | 512 + 240 = **752 frames / 15.667 ms** | **15.7 ms**, contributors 6.3 + 9.3 ms |

The smaller host was explicitly selected as **256 samples / 5.33 ms** in Bitwig's PipeWire System Out settings; rate remained automatic and actually negotiated 48 kHz. Both proxies report vendor float32 only in this fixture. No silent resampling/downconversion. The two smaller-host comparisons used the same saved edited project hash `c92c026c7a8c4b148e7d27b1c9cba197cbccece82a5b6aeea7b844a426b9c624`; the 512 run's later test edit was backed up before restoring that comparison sound for 256.

At host256, native host CPU was 16.101% versus 16.278%; LoFi Windows 38.598% versus 38.685%; FRAGMENTS Windows 24.274% versus 24.517%. The lower setting does not have a demonstrated CPU advantage.

The first 256-delay FRAGMENTS request needed 5.097 ms waiting for reply after 0.401 ms in the queue, but the actual callback consumption budget was only 5.006 ms. LoFi's first missed request 16 had 2.561 ms queued + 2.481 ms reply against 4.472 ms available. Each device had a 256-frame pre-note/startup gap. Later FRAGMENTS request 40178 spent **29.093 ms in native preparation**, followed by a 0.752-ms reply, producing a six-chunk backlog. Similar 28–31-ms preparation intervals occurred at the smaller host with 512 delay, and 24–25-ms native publication-stage intervals occurred in the repaired host512 run. These are localized elapsed intervals, **not yet classified as CPU execution, allocator blocking or runnable scheduling delay**. Heavy tracing was off. The ordinary preparation/publication path contains no deliberate wait, but source inspection alone cannot prove why a thread lost that time. These remaining outliers and startup budgets are the precise reason 256 is not promoted; a clean retry is not their repair.

The repaired heavy-trace startup LoFi request 14 spent **19.904 ms inside vendor process**. Wine thread-CPU accounting advanced by one coarse 10-ms quantum; it does not resolve the rest into blocking versus scheduling. A zero CPU delta elsewhere does not mean zero computation. The old AP12 untraced timeout remains unknown and is not reassigned to the separate known UIA removal crash.

## Actual workflow and preservation

All Bitwig checks used the normal Applications → Multimedia → Bitwig route, with SSH for bridge deployment/status and Moonlight for control. The original AP12 project hash `e44d326d9682e84201e0aec6845a6347c06bbfe8f25c53fa1e50f74525951c4d` was protected. The AP13 Delivery copy remains installed with the edited two-device chain. Existing AP12 one-bar notes and two-bar LoFi Amount / Grain Mix automation were replayed hands-off; AP12's recording proof is reused rather than claiming a new recording campaign.

Real LoFi cutoff changes reached Bitwig (first 488 Hz / normalized 0.476, later the matched 666 Hz / 0.520 gesture). Real FRAGMENTS Grain Volume reached **−2.70 dB / normalized 0.916**. Explicit File → Save captured opaque vendor state for both, with changed project/state hashes. Save while stopped completed. Project reopen and the final Applications relaunch restored both devices and the edited FRAGMENTS host value; both same-instance editors were exercised. The remaining native panel focus-refusal status is retained even where the detached window became visible and editable. No global focus or accessibility settings were changed.

Live-note phrases used Bitwig's on-screen keyboard with clips stopped. Local Deck speaker sink-monitor captures contained nonzero finite audio through both devices at both selected delays. These are software output observations, not physical loopback latency or a human listening judgment. Removing FRAGMENTS in the test copy left the **same LoFi session** running and produced nonzero local output, with no additional LoFi gaps during the 54.178-second bracket. The first removal attempt included an extra delete during UI update; both devices were restored before the clean effect-only test. Neither the attempt nor its restore is presented as sibling-preservation evidence. The saved full chain was reopened afterward.

Bridge software only was reversibly deployed. Installed vendor artifacts, class/parameter IDs, registrations, runtime, environment and per-process `uiautomationcore=` workaround remain. The service remains the automatic owner; no repository checkout, SSH session or preview owner is needed to reopen devices. No new reboot campaign was performed because startup implementation did not change. AP12's accepted restart evidence remains applicable; final normal Bitwig quit/relaunch/reopen was checked here. Heavy tracing is disabled; bounded fault/gap visibility remains.

During the last recall interval, an external operation changed the existing runtime service CPUWeight drop-in from unset to **10000**, with file modification time **2026-09-09 06:36:15 UTC**. This task did not write that setting. All four matched playback intervals finished earlier (04:53:38, 05:49:33, 06:13:03 and 06:24:28 UTC). The final 400.806-second recall/editor interval crossed this change and is not a performance comparison: LoFi had 4 gaps / 5632 missing frames and FRAGMENTS 2 / 3072. The setting was surfaced to the operator and left untouched pending their preference. File times and live properties are retained in `installation-final.json`; they do not supply a per-instant scheduler trace. The performance recommendation does not rely on the raised weight.
