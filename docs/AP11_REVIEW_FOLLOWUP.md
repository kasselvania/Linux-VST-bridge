The FRAGMENTS shared-code follow-up to [review 5142638283](https://github.com/kasselvania/Linux-VST-bridge/pull/76#pullrequestreview-5142638283) is implemented and verified. ## Actual focus handoff

The fixture is the existing SteamOS 3.8.16 KDE Wayland desktop with XWayland clients, KWin 6.4.3, normally Applications-launched Bitwig 6.1, pinned Proton 11 and FRAGMENTS 1.0.0.2925. Moonlight supplied ordinary user input. SSH inspection read window properties, process identity and root activation messages; no synthetic input was used on this desktop.

Diagnostic head `ef00b1a` preserved the old Win32 activation calls while exposing their outcomes and the actual native ButtonPress timestamp. When the existing editor was hidden, the Win32 foreground request returned false, foreground/keyboard flags stayed zero, and no activation request for that target reached the X11 root. Initial old-route activation traffic used source 2, timestamp 0 and requestor 0. The real native click's context was not reaching the desktop activation route. This is an observed failed handoff, not an assertion about every internal KWin policy decision.

Repair `47de063` sends the normal application `_NET_ACTIVE_WINDOW` request on the native UI thread, with the actual click timestamp and requestor window. The Windows owner returns the XID attached to its own parent via Wine's window property; there is no HWND cast, title lookup or second instance. The [EWMH contract](https://specifications.freedesktop.org/wm/latest-single/) permits refusal, as does Microsoft's [SetForegroundWindow contract](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

The native controller uses checked asynchronous XCB replies, at most four ready replies per UI tick, with a two-second target bound and 750-ms desktop confirmation bound. It verifies both active-window and actual keyboard ownership, including bounded child ancestry. A superseded source, destroyed target or stale generation cancels/refuses the operation. Windows then independently verifies foreground, keyboard, enabled and non-iconic state on its owner thread. Only a confirmed result increments `focuses`. Open, focused, refused and unsupported are separate states; refusal leaves healthy audio usable. No global focus policy, permanent topmost flag, XSetInputFocus or pager impersonation is used. The fixed GUI message is now 584 bytes, GUI ABI/protocol 2; audio protocol and mailbox are unchanged.

Both repair builds passed real hidden/minimized checks. In the final session `8901a957…`, the same Windows PID/start-time identity remained through all operations. Hidden activation and restoration from observed `Iconic`/`_NET_WM_STATE_HIDDEN` both confirmed native foreground/keyboard and Windows flags 6 on view epoch 1. Explicit close/reopen created view epoch 2 while retaining the DSP process. Final totals: two opens, two closes, four confirmed focus handoffs, zero GUI failures. A final native-only lifetime guard (`c3f728c`) also binds a late target reply to the earlier timeout denial without retrying expired activation; its production SDK regression covers this case. This guard changes only the expired-response branch, so the successful commercial handoff and audio results below are reused from `f400017`. Auto-open without a real click honestly reports focus unsupported; the panel button supplies the context. Confirmation does not promise continued foreground ownership after later user actions. [Exact focus observations and passive messages](../evidence/AP11/review-focus.json).

## First delayed request and repair

With the focus repair running at 48 kHz/float32, 256-frame Bitwig callbacks, 512 added frames and 192 vendor frames, the first reproduced gap was audio request **14158**, not a queued follower. Request 14156 completed normally; **14157 was a 128,328-byte state capture**. Request 14158 waited 10,519 µs in the native queue, then its audio round trip took 343 µs. The first missed callback contained 256 frames. Callback arrivals around this event were ordinarily spaced, not a burst.

Correlated monotonic request traces and scoped `perf` switch events show the native transport worker off CPU for about 11.974 ms while blocked on the serialized request; this interval also includes any wake-to-run delay. The Windows owner/UI thread spent 8.332 ms continuously scheduled during the state interval. Thus the initiating obstruction was serialized control work, with substantial owner computation, not long DSP computation or a long native-worker preemption. The exact split between vendor state generation and the bridge's state/parameter walk remains unmeasured.

The trigger was concrete: `panelOpen()` queued **Open plus Refresh on every focus click**. Refresh enumerated all 2,348 parameters and ultimately called the host's `restartComponent(kParamValuesChanged | kParamTitlesChanged)`. Bitwig then captured unchanged state. Nine Open commands in this session produced nine such captures, including repeated hidden/minimized focus; the early captures had the same opaque hash. A second gap followed state request 17810 by the same mechanism.

Native-only repair `f400017` removes the unsolicited Refresh. Real vendor restart notifications still carry complete actual values/titles through the existing queue, and required saves retain the serialization barrier. This does not cache fake controls, duplicate DSP edits or permit concurrent unsafe state access. The production SDK controller/processor regression now asserts that repeated focus carries its click context but sends no Refresh, restart or gesture. Its existing actual vendor-refresh and stopped-edit/save assertions still pass.

The final working candidate reused the exact Windows binary and repeated open, hidden focus, minimized restoration, control editing and editor close/reopen with the same input loop and 512-frame configuration. Five Open commands produced **zero focus-related state captures**. Actual control editing and normal close still captured state (requests 38311 and 47707).

| --- | ---: | ---: | ---: |
| Focus repair before invalidation repair | 31,311,872 / 122,312 | 4,352 | 6 / 17 |
| Final native repair | 12,212,480 / 47,705 | 0 | 0 / 0 |

Both have 512 priming frames, no rejected callbacks, no observer drops or unretained gap records, and clean contained close. Every before gap is preserved with its absolute clock. Later 12-ms reply and approximately 29–31-ms native preparation stalls remain unclassified; they occurred outside the bounded profiler window. Removing the demonstrated focus dependency does not explain those historical outliers.

This is a causal comparison, not equal-duration statistical reliability qualification: the sessions cover 652.33 and 254.43 audio seconds. The final session includes the newly recorded .5/0 curve; early before playback used .5. A scoped 240-second user-mode profiler was present during the first two before gaps, but no profiler or strace ran in the final session. The absence of false captures and the production regression establish the mechanism repair; unequal durations/instrumentation preclude claiming a general gap-rate speedup. ## Recorded gesture and actual sound

The first complete Touch gesture made a brief dip. A second complete Latch gesture on the real Grain Mix knob wrote a held zero section, approximately bars 1.4–2.3 of the existing bars 1–3 loop, with .5 outside. Writing was then disabled. Bitwig's visible lane, hands-off playhead, vendor knob and ordered consumed Windows controller commands all followed that pattern. The processing instance was unchanged. The recorded project was saved privately and replayed again on the final repaired candidate; this was the same affected automation fixture, not a new recall campaign.

The local Deck sink capture supplies sound evidence independent of Moonlight. After aligning one complete input loop, quarter-beat stereo windows inside the held zero region fit the original dry input at gain about .316227734. Relative residual was at most **2.51e-8** in the recorded replay and **1.29e-6** in the final replay. Outside the zero region, residual was .161–.390 and .078–.401 respectively: output includes the effect's processing. Before recording, the same region remained processed. This establishes that audio follows the recorded dry/processed change, not just a moving cached slider. Alignment lag is arbitrary recording alignment and is not a bridge-latency measurement.
