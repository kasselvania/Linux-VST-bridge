# MF3 — Managed preparation and qualification

MF3 projects installation, inspection, prepared artifacts, publication, evidence,
review and live ownership separately. It is stacked on SV1 PR #107 at
`d4b863837814b6e5f889952226dadb28798caae2`; that PR and its working checkout are
not merged or modified by MF3.

## Operator workflow

The native manager offers an exact discovered **audio class**. Controllers are
shown as technical associations, not additional instruments. `Check compatibility`
uses the isolated inspector for that class, or retains an exact current prior
inspection. This preliminary check does not establish DAW audio, editor,
automation or persistence behavior.

`Prepare test instance` builds immutable candidate artifacts in a background
manager operation. It does not publish. `Enable experimental use in Bitwig` is an
explicit, separate operation using the existing publication transaction owner.
The card says experimental; it does not say supported. Closing the frontend does
not stop audio, withdraw publication or forget the operation.

`Disable experimental use / restore previous publication` restores the exact
ordinary ancestor if one exists. Otherwise it removes only the experimental
publication. Installation, candidate and evidence history remain. An absent
ordinary predecessor is not fabricated.

Operator observations carry their original source and a durable ordinal. DAW
load, MIDI, audio, editor, parameters, automation, state recall and retirement
remain separate results. Unobserved behavior stays not tested. A later passing
checkbox cannot erase a retained failure. MIDI is not a required instrument
contract for an effect. An explicit local maintainer review is separate from
recording observations and from publication. Acceptance needs complete relevant
passing product observations, no retained failure, and an exact evidence digest.
Changed observations block a new acceptance; an existing ordinary publication
retains its sealed decision until explicit withdrawal. Local acceptance is
not a project-wide vendor or platform support claim.

The ordinary publication button uses the same immutable product bytes and stable
native IDs. It changes only policy revision, claim and review evidence. Incomplete
Serum evidence keeps this crossing unavailable; MF3 does not qualify Serum.

## Canonical records and authority

Operator model 4 adds only closed selection/candidate operations. Paths, commands,
compiler arguments, profiles, process IDs, source files and environment variables
cannot be submitted by the frontend. Bounded observation/review text is evidence,
never executable authority. Manager dispatch revalidates offered state and
inactivity; button disabled reasons are presentation only.

Preparation schema 1 binds:

- full managed environment and runner identity;
- module digest and selected factory audio class;
- original scanner artifact/source and complete factory report;
- supervised inspection, actual controller association and cleanup;
- exact descriptor, native image, source recipe and Windows host;
- preparation origin, including retained SV1 provenance.

Records are immutable and content-addressed below the manager's private
`preparation` namespace. Separate observations and decisions refer to that exact
candidate. Their small revision token participates in operator stale-request
checks. Private reports and build work remain private; public examples must omit
local paths, process IDs, account data and vendor content.

Installation history remains readable after the environment acquires a product
registration. Its initial-install mutation route stays closed. The instrument
handoff does not hide other audio classes such as Serum 2 FX. Older cancelled
attempts are labelled and collapsed. A missing VST3 directory yields an empty
inventory, not a misleading generic operating-system error.

## Fixed preparation recipe

The optional immutable software package `preparation-kit.zip` contains owned
native sources, the registered Rust archive, a pinned recipe including its exact builder and descriptor generator, and a separately
built preparation Windows host/source manifest. No vendor module, installer,
SDK distribution, account or preset is packaged. Omitted kit updates retain the
previous exact kit, as with the frontend.

`tools/mf3/package_kit.py` is maintainer packaging, not an operator command.
The manager uses the existing `tools/ap8_descriptor.py` rules and the existing
native CMake target. No product-name dispatch or new per-product qualification
enum is needed. The generic route uses one `managed_experimental` authority.
Unsupported bus/interface/controller facts stop at a specific boundary.

The already installed official SDK and Flatpak SDK are checked against their
pinned identities. There are no downloads, shell commands from the UI or ambient
compiler selections. Missing prerequisites are shown as a package prerequisite.
CMake runs offline with only the owned build directory and read-only SDK exposed.
Output is drained after its 32 KiB retention limit. Build turns and archive/file
sizes are bounded; worker cgroup retirement owns descendants. Uncommitted work
is removed by the operation finalizer; committed native artifacts are retained.

The preparation host adds the actual `getControllerClassId` result to inspection
metadata. It does not replace the default installed host used by existing
products. New generic candidates bind the preparation host; SV1 adoption keeps
its original host and native bytes. The retained SV1 inspection did not record
that returned controller ID, which is explicitly shown as unavailable; factory
name/order is not substituted for it.

## Lock and publication laws

The operator order remains canonical serialization, bounded registry readback,
then action-specific ownership. Compilation, hashing and native package copying
run outside global registry authority. Preparation and inspection use the
operation-bound suspend/recovery owner. A fresh short guarded check precedes
candidate commit.

Generic publication copies an immutable revision before exposing a transaction
or physical pointer, then rechecks registry bytes, inactivity and the prior
physical publication under the commit lock. The existing intent, pointer,
reconciliation and completion machinery performs the commit. Interrupted copies
cannot grant admission. Audio/service lock acquisition remains fail-fast.
Generic experimental publications are not automatically restored by polling,
frontend close or service restart. A new class has one experimental DSP slot
under the unchanged global ceiling; no capacity or performance qualification is
inferred.

## Source rereview repair: immutable generations and publication-time acceptance

The reviewed `4fd1cf6` implementation and its installed/live evidence remain
historical facts. The following repair is source-only until independent review;
no new package, candidate publication or product session has been deployed.
Operator model **4** adds exact inspection/recipe/predecessor preparation inputs,
a separately requested inspection refresh, exact expected-current replacement,
and ordinary withdrawal. Old frontend requests cannot silently become new actions.

A selection has a history of immutable inspections and candidates. Inspection
identity hashes the complete report/host/source record, rather than the report
alone. Retention order selects the most recent observation under the current
inspection host; candidate-bound old observations remain readable. A missing or
superseded current inspection offers refresh, never automatic reinspection.

Candidate identity includes exact selection, inspection, policy, native and
descriptor, host/source, recipe and preparation evidence basis. Lineage separately
records the preparation identity, ordinal and declared predecessor. Preparation
may reuse an exact native output while creating distinct metadata for a changed
review/evidence basis. A repeated unchanged preparation reuses the same candidate;
ambiguous different outputs for the same build inputs are refused. New generation
metadata never overwrites the old candidate, observations or decisions.

SV1 adoption materializes its original candidate identity and provenance in
private immutable generic history. It retains exact copies of the originally
bound environment, onboarding and inventory records, original profile and
qualification authority, inspection, native/host/source identities and original
session evidence. Later scanner or inventory changes affect current eligibility,
not readability. The legacy route verifies that provenance directly and never
passes `retained-sv1` to preparation-kit verification. Its original identity remains
unchanged; the history view identifies the durable provenance by its digest.

Publication readback distinguishes unpublished, removed, experimental, ordinary,
needs-attention and another-configuration states. Current revision/profile and
physical consistency remain visible even while another candidate is displayed.
Needs-attention cannot offer generic Enable. Replacing a different publication
requires the exact expected current revision ID/digest and replacement candidate;
the publication owner compares this again under its mutation guard. Withdrawal
and experimental removal retain installation and all history.

Acceptance uses **policy A: publication-time authority remains valid until
explicit withdrawal**. An ordinary profile binds an immutable explicit decision.
Later evidence remains visible and prevents a new acceptance/publication, but
does not silently revoke that existing profile in service admission. The manager
shows the sealed publication and new review requirements together; the exact
Withdraw action removes it. New observations cannot rewrite the original decision.
Generated tests exercise a later exact failure, matching UI/runtime authority and
explicit withdrawal.

Preparation-kit schema **2** contains the actual native builder and descriptor
generator sources in its hashed file roster. The manager's small loader verifies
the exact kit and these bytes before executing either kit-owned implementation.
The build result retains kit, builder and generator hashes; candidate reuse checks
that complete result. Schema-1 kits remain historical runtime provenance but
cannot borrow newer manager-embedded generators to create a new candidate.

`processing_restart` is a separate required evidence area. The retained SV1
projection records its restart failure there, normal retirement as not tested,
and positive terminal cleanup separately. No historical evidence file is edited,
and no LC2 behavior or Serum lifecycle repair is included.
