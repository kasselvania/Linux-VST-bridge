### Startup and capacity ownership

`native-audio-client::admission` owns the closed startup codec. `LVB3\n` carries the established 16-byte class plus 32-byte module digest followed by a fresh 16-byte request nonce. The response is u16 length (at most 1,024 bytes), `LVR3`, one status byte, three zero reserved bytes and the exact nonce. Success adds a nonzero 16-byte session, u32 delay and an absolute UTF-8 directory; refusal has no payload or ownership. The saturated connection-classifier may send only the zero-nonce ServiceBusy refusal. No zero-nonce success is accepted. Only typed ServiceBusy can retry, with 64 attempts/20 ms backoff inside the single ten-second startup deadline, entirely outside audio processing.

The service checks capacity under its existing registry lock before registration validation and session creation. The lock serializes unexposed reservation; the existing exact durable lease owns capacity after exposure. Maintenance releases that lock after its lease is published, so status remains available during vendor access. Positive supervisor `LVO1 <exact-session> retired` plus physical transport absence precedes lease removal. Wait/read failure, mismatched receipt or failed unlink retains the lease and blocks new admissions; no completed sibling is substituted. Startup reconciliation retains the existing independent ownership-receipt law.

## Why capacity needs a separate slice

Three different statements currently coexist:

1. The manager service retains at most eight live client threads.
2. The native backend contains a four-slot generation-checked registry.
3. The manager documentation says eight simultaneous instance admissions are supported but explicitly says that this is not a measured eight-instance performance result.

They are not the same claim.

The eight-thread check is currently a service implementation mechanic. It occurs before the connection greeting is classified, so maintenance requests and DSP sessions share it. A ninth connection is dropped with no typed capacity response.

The four-slot registry is compiled into the Rust static library and linked into each generated native VST3 shared object. Its practical scope depends on how Bitwig groups plug-in instances and modules into native host processes. Four may mean:

- four instances per native module image in one Bitwig host process;
- four instances per Bitwig plug-in host process;
- four instances per class;
- or a limit that never binds under the current Bitwig sandbox mode.

AP17 must observe the real process/module topology before selecting or changing a limit.

Every DSP instance also creates its own supervised Windows host process and its own 661,204-byte hot transport set under the current protocol. The main scaling risk is therefore not the tmpfs footprint alone. It includes Windows process memory, threads, scheduling, editor/controller work, project state, and cumulative serial latency.

## Initial source map

### Manager service

`bridge-manager/src/main.rs::serve` currently:

- owns the service socket;
- reconciles prior leases;
- starts one thread per accepted client;
- removes finished thread handles;
- drops new connections when `threads.len() >= 8`;
- uses the same thread set for inspection, qualification, vendor access, and DSP;
- allocates a DSP tmpfs session only after registration and visibility checks;
- exposes native ownership before launching the supervisor;
- blocks future admissions when cleanup cannot be confirmed.

The existing positive-retirement and lease laws should be preserved. Capacity accounting should integrate with them rather than create a second cleanup authority.

### Native backend

`native-vst3-proxy/backend/src/instances.rs` owns:

- four fixed slots;
- generation-derived handles;
- nonblocking lease acquisition;
- exclusive update/removal;
- stale-handle refusal;
- per-slot startup and teardown ownership.

`native-vst3-proxy/backend/src/queued.rs` owns one live transport per inserted registry value.

`native-vst3-proxy/CMakeLists.txt` statically links the same Rust archive into each generated VST3 module. Dynamic-loader/process scope must be established on the Deck.

### Windows and supervision

Each admitted bridge instance currently has:

- one Python supervisor;
- one Windows host process cohort;
- one mapped audio/control/UI/status transport;
- one editor and controller owner;
- one durable lease/result path;
- one tmpfs session.

The environment keeper is a separate non-DSP owner.

This process-per-instance design provides strong isolation. AP17 should preserve it unless the measured envelope proves that it is the limiting owner and a later architecture decision is warranted.

### 1. Baseline readback

Before constructing a larger project, retain:

- both revision-7 profiles/publications and revision-3 rollback;

- current service/keeper/PID-start identities;
- current CPUWeight and power state;
- trace disabled;

### 2. Topology probe

Create two instances of one class without changing the host mode.

For each instance, correlate:

- Bitwig device identity;
- native VST3 module path;
- Bitwig plug-in host PID/start;
- native session ID;
- supervisor PID/start;
- Windows host PID/start;
- class ID;
- tmpfs device/inode.

Repeat with both classes. Determine which instances share a Linux process/module image and which do not.

### 3. Same-class escalation

Use a protected project and add one instance at a time.

For Pure LoFi and then FRAGMENTS:

```text
1 -> 2 -> 3 -> 4 -> one additional attempt
```

At every step:

- wait for all sessions to settle;
- verify the expected number of native/Windows owners;
- run a short active musical interval;
- inspect fault and delivery counters;
- open at least one editor;
- remove the newest instance;
- verify exact capacity reuse before continuing.

If the fifth instance succeeds because Bitwig isolates images/processes, do not claim the native four-slot limit is irrelevant. Record its true scope and continue only within the service and machine stop conditions.

### 4. Mixed parallel projects

Construct balanced mixed projects incrementally. Prefer independent tracks first so CPU/process scaling is not confused with serial delay.

A candidate matrix may include:

```text
1 LoFi + 1 FRAGMENTS
2 + 2
3 + 3
4 + 4
```

Only run the next row when the prior row is safe and trustworthy. The selected maximum may be an intermediate row.

### 5. Serial topology

Build a small set of increasing serial depths with clear routing.

For each depth retain:

- exact device order;
- per-device reported latency;
- total reported chain latency;
- host compensation/readback where available;
- active output;
- missed/expired frames;
- CPU/resource cost.

Do not conflate serial chain depth with total service capacity. A project may support many parallel instances but only a shallow live-monitoring chain.

### 6. Maximum-project qualification

At the selected useful maximum:

- give every instance unique visible state;
- save a protected project copy;
- run two independent trace-off musical intervals;
- open two vendor editors simultaneously;
- close/reopen editors without changing DSP instances;
- save, close, and reopen;
- verify every same-class state remains assigned to the correct instance;
- retire normally.

A clean interval supports only the exact fixture/workload. It is not a hard real-time guarantee.

## Selecting the supported maximum

The selected limit should be the largest tested configuration that satisfies all of:

- no terminal bridge/vendor/DAW fault;
- no unresolved owner or lease;
- no reproducible active-musical failure caused by the added load;
- stable project save/reopen;
- stable same-class state identity;
- desktop and DAW remain operable;
- no dangerous memory/swap/thermal condition;
- positive individual and complete retirement;
- deterministic over-limit behavior one step above it.

If resource pressure appears before an architectural hard cap, select the lower resource envelope and retain the higher hard cap separately.

## Admission model

The implementation should probably introduce an explicit service-owned DSP admission state, but private types and organization remain implementation choices.

The law must be:

```text
capacity checked and reserved
-> registration/profile/performance remain exact
-> tmpfs session and lease created
-> native binding exposed
-> supervisor/Windows owner launched
-> live ownership retained
-> positive retirement received
-> capacity released exactly once
```

Failure before exposure returns the reservation. Failure after exposure follows existing conservative lease/blocked-admission behavior.

The service-worker pool is not the product counter. Maintenance routes should remain bounded but distinct:

- keeper is not a DSP slot;
- inspection/qualification require their existing environment conditions;
- vendor access is not a normal DSP project slot;
- maintenance may be refused while the project is active without consuming hidden DSP capacity.

A clean over-limit response may require a new owner-socket reply shape. If so, preserve an absolute startup deadline and make the new response explicit, bounded, and versioned. The native proxy should retain a stable error suitable for Bitwig/device diagnosis; it must not wait ten seconds for a connection the service intentionally refused.

## Resource collection

Use existing PID/start ownership. Add only bounded external or manager-owned observation.

At each configuration retain:

- logical instance count by class;
- Linux native host process count;
- supervisor count;
- Windows process/tree count;
- thread count;
- RSS/private memory per owned cohort;
- total available memory, swap, and PSI;

Use exact start identities so exited/reused PIDs cannot be misattributed.

No process walk, filesystem read, allocation, logging, or capacity lock belongs in the audio callback.

## Refusal proof

The over-limit attempt must show:

- a stable capacity reason;
- no Windows process launch;
- no new tmpfs session;
- no durable lease;
- no editor;
- no registration/publication mutation;
- no fault in existing siblings;
- no capacity counter leak;
- one later successful admission after retirement.

A refusal after partial ownership is not an acceptable product limit.

## Same-class state proof

Use distinct state in each repeated instance—for example different macro values and, where safe, distinct presets or effect settings.

After save/reopen:

- instance count and order match;
- visible values match each intended instance;
- opaque state identity remains independently bound where available;
- no two same-class devices collapse to one saved state;
- opening one editor controls only its own instance;
- removing one leaves every sibling unchanged.

Do not put opaque vendor state in Git evidence.

## Failure isolation

Select one exact instance by class, session, PID, and start time. Use the narrowest safe existing failure mechanism.

Expected result:

- the selected instance enters explicit failure;
- siblings keep processing;
- siblings retain editors and state ownership;
- failed transport cannot publish future/stale output;
- supervisor contains only its owned process cohort;
- exact cleanup remains inspectable;
- removing/reloading the failed device creates a fresh identity;
- no automatic guessed-state recovery is claimed.

The test is about isolation, not silent self-healing.

## Restart and reboot reality

### Service restart

With Bitwig closed:

- service stops without unexplained leases;
- keeper retires;
- service starts from installed immutable software;
- tmpfs root marker is valid;
- new keeper becomes ready;
- saved maximum project opens unchanged.

### Unexpected service loss

Use a smaller disposable project because all live owners are intentionally affected.

- existing native instances must fail explicitly;
- no hidden Windows processes remain;
- uncertain cleanup blocks rather than disappears;
- after owned cleanup/reconciliation, saved project reopen creates fresh sessions.

### Reboot or graphical-session restart

- Bitwig is saved and closed first;
- `/run/user/...` session directories disappear by design;
- durable software/profile/publication/environment/project data persists;
- service and keeper recreate;
- the maximum supported project reopens;
- no stale tmpfs identity is trusted.
