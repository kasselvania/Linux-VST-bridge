# AP10 — delivery stalls and commercial effects

PR #71 includes the R1 callback-payload lifetime repair described below and remains unmerged for focused rereview. The earlier production SDK and Steam Deck Serum/FRAGMENTS results are retained at their recorded sources; the R1 verification is a focused native SDK regression, not a new commercial or latency replay. The same-binary socket/mailbox comparison demonstrates lower delivery overhead; 512 frames remains recommended. AP8 #67 and AP9 #69 remain unchanged dependencies. This does not explain the historical engine crash or establish universal plug-in or long-session low-buffer support.

## R1: callback payload lifetime

[Review 5136589052](https://github.com/kasselvania/Linux-VST-bridge/pull/71#pullrequestreview-5136589052) identified a real final-handoff defect at reviewed head `ce1c393`: `Processor::deliverResults` refilled one packet, while `Output::deliver` gave the host pointers into that packet. The pinned SDK `EventList::addEvent` copies the `Event` structure, including pointers. A later drain could therefore replace earlier SysEx/UTF-16 data before the host consumed it. The original collector tests and production SDK consumer copied payloads immediately; their retained passes did not establish shallow-host callback lifetime.

`Output` now has 512 preallocated, UTF-16-aligned 512-byte payload slots per processor: 262,144 backing bytes, matching the pending queue's maximum 512 events. Requested payloads receive distinct slots before `addEvent`. The slot cursor resets once at guarded `process` entry, including zero-frame callbacks; it does not reset between drains, at callback return, or on a stop request. Submitted bytes remain intact through host consumption until the next callback. Exhaustion increments the existing rejection counter and follows the existing latched failure/silence path; it neither overwrites an earlier payload nor defers a due event. Null/inactive sinks, scalar note cleanup, event offsets and parameter delivery retain their existing rules.

The new native regression compiles the actual `Processor::process` implementation and uses the pinned SDK EventList. A controlled backend C ABI supplies multiple SDK-encoded packets; verification reads every byte/code unit only after the full callback returns. On the reviewed production code, nine 512-byte SysEx events in two drains fail with `earlier SysEx overwritten after process return`, while the original collector suite passes. The repair passes that reproducer, odd-size SysEx mixed with all three UTF-16 event types, 512 payloads across 64 drains on three successive callbacks, a zero-frame 512-payload callback, and a forced 513th-payload failure. All first 512 payloads remain valid after that failed callback; subsequent processing stays failed and audio is explicitly silenced. The existing callback audit records zero effects on all tested success/failure callbacks. Original collector tests still pass unchanged.

These tests and the native proxy build passed on the Deck's retained GCC 15.2.0 / Freedesktop SDK 25.08 build lane, reached through Tailscale. CI also builds this native regression against the same pinned VST3 SDK. Exact source blobs, binary hashes and red/green results are in `evidence/AP10/r1-payload-lifetime.json`. The native result source changes only; the Rust queue, Windows binary, protocol, fixed delay and commercial evidence are reused unchanged. The test's controlled backend does not exercise Windows scheduling, mailbox delivery or a commercial plug-in; no new claim is made for those layers. No Bitwig session or published device plug-in was changed for this fix.

## Return-path repair and current verification

Protocol minor 9 carries bounded process results in the existing mailbox (mailbox layout version 2). Each completion allows 64 events, 128 parameter points and 4,096 payload bytes, with 512 bytes per event payload. The fixed C ABI is separately versioned. Both endpoints use the same capacities; older protocol modes receive null output collectors rather than being asked for values they cannot transport. Bus metadata, implemented support and host-selected activation are separate: the original default-active flags are preserved, and a supported main output can be explicitly activated even when default-inactive. Auxiliary activation remains unsupported.

Windows collectors copy the pinned SDK's ten event variants, including signed note IDs, bus/flags/PPQ, note expression values, chord/scale, legacy MIDI, and bounded UTF-16/SysEx payloads while their source pointers remain valid. Parameter feedback has a separate bounded list. No SDK objects or pointers cross the process boundary. Collector refusal is latched even if a plug-in ignores its return value.

The native completion queue admits process results before audio expiry. Presentation is P+s+D with bridge delay D added once, preserving vendor PPQ and producer order at equal offsets. Future values remain in preallocated storage (512 events/1,024 points); late valid values are delivered once at offset zero and counted. Zero-frame parameter flush results are eligible without advancing the sample clock. Events retain P+s+D even when produced by a zero-frame call; a due event can also be delivered by a zero-frame callback. Expiring accompanying audio does not discard a returned note-off or fault an otherwise healthy instance. AP7's missing/expired audio counters remain independent.

Only the current process callback's output sinks receive SDK calls. Null sinks and inactive buses count as host-unrequested and are not replayed later. Malformed values, fixed-capacity overflow and SDK addEvent/addPoint refusal produce explicit failure. The native processor tracks up to 512 notes actually handed downstream. Stop/reset or terminal failure requests bounded best-effort note-off delivery in a valid callback; unavailable/rejected cleanup and unreleased notes are reported honestly. No future/stale work is replayed across generations. `discarded_on_reset` counts values already in the native pending presentation store, not every unpublished Windows result.

The original Windows SDK fixture and native consumer exercise real output activation without a default-active flag, every event variant, field values and copied payload lifetime, parameter IDs/values/timing, variable/chunked blocks, a deliberately delayed note-off, null/inactive sinks, overflow, SDK refusal, zero-frame flush and stop cleanup. The consumer ran through the real Windows mailbox and native callback on the Deck: all ten SDK event variants, five parameter points, exact P+s+D timing across variable blocks, copied pointer payloads, and zero-frame parameter flush passed. A deliberately stalled note-off arrived 697 frames late, once at offset zero, despite 960 missing/expired audio frames. One downstream held note was released on stop. Null and inactive sink cases passed without replay. See `evidence/AP10/return-path-production.json` for the original observations and exact binaries.

At production source e4df377, all 40 Rust backend tests pass, including the actual callback/completion regression retaining a late note-off after expired audio and admitting zero-frame feedback. Clippy with warnings denied passes. The pinned-SDK C++ test passes for all variants, copied payloads, activation support, null/inactive delivery, cleanup and finite bounds; the native processor/consumer syntax checks pass. Additional focused tests check aggregate payload/parameter capacity and a real SDK addPoint refusal. The zero-frame event/parameter distinction was then checked with the full 40-test backend suite and Clippy, both passing. Windows host/fixture builds through e4df377 (run 34091094784) and the native 94c762c build pass; the earlier native 68059fd build's warning failure is retained. ## Causal finding and first repair

The retained AP9 two-note Serum clip at 48 kHz / float32 / 128 host frames / 256 added frames reproduced its first stall around transport request 9855–9856. Callback admission remained regularly spaced at about 2.67 ms. The delayed followers accumulated queue time only after that first request.

With the socket path, a trace-only run put 5.41 ms inside Windows reply send while the Serum process call took 149.9 µs. In the scheduler-instrumented reproduction, the first request instead stalled in receive: Windows audio was blocked for 6.451 ms, a contemporaneous wait-channel sample was `anon_pipe_read`, and wineserver ran on CPU throughout that entire interval. Serum's process call took 141.2 µs. The Linux transport worker was blocked awaiting the response. This is a synchronous Wine-server dependency, not evidence of slow synthesis or a host callback burst. The specific server operation monopolizing that interval was not identified.

The candidate adds a versioned, identity-bound shared-memory mailbox for existing audio request/reply frames. Lifecycle, state and supervision retain their existing socket/owner contract. Fixed delay and ordered sequence/epoch/position checks are unchanged. Every issued request retains its five-second failure deadline; missed presentation spans are counted while waiting. The callback still only copies into preallocated queues and never waits for either endpoint.

QPC's observed resolution was 100 ns. Linux monotonic/Instant correlation brackets were below 1 µs. Matching request/reply bounds limited the inter-clock offset uncertainty to 303.226 µs in the trace-only baseline and 198.366 µs in the scheduler baseline. Scheduler intervals use one Linux monotonic clock. Cross-clock durations were not obtained by assuming equal clock origins.

## Historical Serum regression and closed decision

Normally launched Bitwig failed to activate the current Serum proxy before any audio callback. The bounded owner-thread diagnostic at native source 86d26cf records `activateBus(kEvent, kOutput, 0, true)`. Serum declares this main output bus with 16 channels. AP10 retains that SDK census and marks output events inactive, but Bitwig explicitly requests activation. Native and Windows activation policy reject event outputs; the process protocol and C ABI carry input events only. See `evidence/AP10/serum-bus-activation.json`.

This is an AP10 integration regression, not a vendor failure. AP9's proxy exposed only its hard-coded note input and audio output. Earlier AP10 Serum playback used that older bus shape, so it cannot qualify the final implementation. No output events were observed in this reproduction because processing never started. Accepting activation without a return path would silently discard any emitted events; deleting or relabeling the bus would contradict the current exact-bus requirement.

Review 5128434219 and the updated CURRENT_SLICE closed the return-path decision. The implementation and current verification limits are recorded above. The earlier handoff is retained as historical context, not a request for another approval document or slice.
