# AP10 — delivery stalls and commercial effects

AP10 is incomplete and PR #71 remains draft/unmerged. The return-path decision in CURRENT_SLICE and review 5128434219 is implemented in this PR: returned events and parameter feedback use the existing mailbox/completion queue, and both endpoints support declared main event-output activation. Local regressions pass, but the new SDK producer/consumer device run and current-candidate Serum playback/recall/close, affected FRAGMENTS checks and matched 256/512 comparison are still outstanding. AP8 #67 and AP9 #69 remain unchanged dependencies. Keep 512 recommended.

## Return-path repair and current verification

Protocol minor 9 carries bounded process results in the existing mailbox (mailbox layout version 2). Each completion allows 64 events, 128 parameter points and 4,096 payload bytes, with 512 bytes per event payload. The fixed C ABI is separately versioned. Both endpoints use the same capacities; older protocol modes receive null output collectors rather than being asked for values they cannot transport. Bus metadata, implemented support and host-selected activation are separate: the original default-active flags are preserved, and a supported main output can be explicitly activated even when default-inactive. Auxiliary activation remains unsupported.

Windows collectors copy the pinned SDK's ten event variants, including signed note IDs, bus/flags/PPQ, note expression values, chord/scale, legacy MIDI, and bounded UTF-16/SysEx payloads while their source pointers remain valid. Parameter feedback has a separate bounded list. No SDK objects or pointers cross the process boundary. Collector refusal is latched even if a plug-in ignores its return value.

The native completion queue admits process results before audio expiry. Presentation is P+s+D with bridge delay D added once, preserving vendor PPQ and producer order at equal offsets. Future values remain in preallocated storage (512 events/1,024 points); late valid values are delivered once at offset zero and counted. Zero-frame flush results are eligible without advancing the sample clock. Expiring accompanying audio does not discard a returned note-off or fault an otherwise healthy instance. AP7's missing/expired audio counters remain independent.

Only the current process callback's output sinks receive SDK calls. Null sinks and inactive buses count as host-unrequested and are not replayed later. Malformed values, fixed-capacity overflow and SDK addEvent/addPoint refusal produce explicit failure. The native processor tracks up to 512 notes actually handed downstream. Stop/reset or terminal failure requests bounded best-effort note-off delivery in a valid callback; unavailable/rejected cleanup and unreleased notes are reported honestly. No future/stale work is replayed across generations. `discarded_on_reset` counts values already in the native pending presentation store, not every unpublished Windows result.

The original Windows SDK fixture and native consumer exercise real output activation without a default-active flag, every event variant, field values and copied payload lifetime, parameter IDs/values/timing, variable/chunked blocks, a deliberately delayed note-off, null/inactive sinks, overflow, SDK refusal, zero-frame flush and stop cleanup. The consumer is implemented but **has not yet run through the real Windows mailbox on the Deck**. Codec/unit passes are not that proof.

At production source e4df377, all 40 Rust backend tests pass, including the actual callback/completion regression retaining a late note-off after expired audio and admitting zero-frame feedback. Clippy with warnings denied passes. The pinned-SDK C++ test passes for all variants, copied payloads, activation support, null/inactive delivery, cleanup and finite bounds; the native processor/consumer syntax checks pass. Additional focused tests check aggregate payload/parameter capacity and a real SDK addPoint refusal. Windows host/fixture builds through e4df377 (run 34091094784) and the native 94c762c build pass; the earlier native 68059fd build's warning failure is retained. These build results do not establish restored commercial playback. Exact development provenance and unverified items are in `evidence/AP10/return-path-development.json`.

Device deployment is currently paused by automatic tool approval review, which requires explicit authorization to transfer this PR's Windows host, original SDK test module and hash metadata to the existing Deck test-input directory. The destination was reverified as the same Deck/AP10 workspace. No transfer workaround was attempted, no new commercial instance was launched, and the previously restored fixture remains intact. This is a platform transfer gate, not an unresolved return-path design decision.

## Causal finding and first repair

The retained AP9 two-note Serum clip at 48 kHz / float32 / 128 host frames / 256 added frames reproduced its first stall around transport request 9855–9856. Callback admission remained regularly spaced at about 2.67 ms. The delayed followers accumulated queue time only after that first request.

With the socket path, a trace-only run put 5.41 ms inside Windows reply send while the Serum process call took 149.9 µs. In the scheduler-instrumented reproduction, the first request instead stalled in receive: Windows audio was blocked for 6.451 ms, a contemporaneous wait-channel sample was `anon_pipe_read`, and wineserver ran on CPU throughout that entire interval. Serum's process call took 141.2 µs. The Linux transport worker was blocked awaiting the response. This is a synchronous Wine-server dependency, not evidence of slow synthesis or a host callback burst. The specific server operation monopolizing that interval was not identified.

The candidate adds a versioned, identity-bound shared-memory mailbox for existing audio request/reply frames. Lifecycle, state and supervision retain their existing socket/owner contract. Fixed delay and ordered sequence/epoch/position checks are unchanged. Every issued request retains its five-second failure deadline; missed presentation spans are counted while waiting. The callback still only copies into preallocated queues and never waits for either endpoint.

QPC's observed resolution was 100 ns. Linux monotonic/Instant correlation brackets were below 1 µs. Matching request/reply bounds limited the inter-clock offset uncertainty to 303.226 µs in the trace-only baseline and 198.366 µs in the scheduler baseline. Scheduler intervals use one Linux monotonic clock. Cross-clock durations were not obtained by assuming equal clock origins.

## Preserved comparisons and limits

Numerical observations are in `evidence/AP10/delivery-comparisons.json`. Native trace-only baseline source was 7f0bdb8 and Windows source c629a44; mailbox endpoints were ef1bebb. All used the same copied AP9 project, local audio and normally launched Bitwig. Perf targeted owned delivery/server threads; detailed histories were bounded and drained after processing.

- Socket baselines each counted two late 128-frame blocks at startup.
- The mailbox session's first missing output occurred only near request 137508, after roughly six minutes of processing. That event had 31.903 ms in reply preparation, 124.4 µs in Serum process(), and caused 19 late blocks. Scheduler capture had already ended; this event's blocking/CPU/scheduling cause is **unknown**. The mailbox session was not gap-free.
- Perf in that mailbox run began about 35 seconds after native startup. It does not provide a matched scheduler view of the original startup interval. Whole-session counters establish no earlier gap, not identical wineserver work.
- The untraced 256-frame session counted zero missing frames across 36,262 host blocks. Its 40-second local-audio/CPU window used 33.042 CPU-seconds for the supervised cohort versus 36.568 in the trace-only socket baseline. Tracing differs, so that approximately 10% reduction is provisional.
- Untraced 128 frames counted 3,840 missing frames across 74,068 blocks. It is not a recommended setting from this result.

The first mailbox candidate used C++ `sleep_for(50 us)`. Its trace shows approximately 1.06 ms wait increments, adding avoidable wakeup quantization. The implemented repair uses `NtDelayExecution` with the same requested 50 µs interval; the owner-thread comparison below measured the reduced quantization. A matched musical-load result for the final candidate remains incomplete. This is not a priority change or a new runtime.

Keep 512 frames as the established comparison/recommendation until subsequent actual results support a narrower claim. Hardware/converter latency is excluded; Moonlight is only the control surface.

## Historical Serum regression and closed decision

Normally launched Bitwig failed to activate the current Serum proxy before any audio callback. The bounded owner-thread diagnostic at native source 86d26cf records `activateBus(kEvent, kOutput, 0, true)`. Serum declares this main output bus with 16 channels. AP10 retains that SDK census and marks output events inactive, but Bitwig explicitly requests activation. Native and Windows activation policy reject event outputs; the process protocol and C ABI carry input events only. See `evidence/AP10/serum-bus-activation.json`.

This is an AP10 integration regression, not a vendor failure. AP9's proxy exposed only its hard-coded note input and audio output. Earlier AP10 Serum playback used that older bus shape, so it cannot qualify the final implementation. No output events were observed in this reproduction because processing never started. Accepting activation without a return path would silently discard any emitted events; deleting or relabeling the bus would contradict the current exact-bus requirement.

Review 5128434219 and the updated CURRENT_SLICE closed the return-path decision. The implementation and current verification limits are recorded above. The earlier handoff is retained as historical context, not a request for another approval document or slice.
