# AP10 — delivery stalls and commercial effects

AP10 is incomplete and PR #71 remains draft/unmerged. Delivery and FRAGMENTS repairs are retained, but the current SDK bus implementation prevents Serum instrument activation in Bitwig. The concrete return-event boundary is described below and in `AP10_HANDOFF.md`. AP8 #67 and AP9 #69 remain unchanged dependencies.

## Causal finding and first repair

The retained AP9 two-note Serum clip at 48 kHz / float32 / 128 host frames / 256 added frames reproduced its first stall around transport request 9855–9856. Callback admission remained regularly spaced at about 2.67 ms. The delayed followers accumulated queue time only after that first request.

With the socket path, a trace-only run put 5.41 ms inside Windows reply send while the Serum process call took 149.9 µs. In the scheduler-instrumented reproduction, the first request instead stalled in receive: Windows audio was blocked for 6.451 ms, a contemporaneous wait-channel sample was `anon_pipe_read`, and wineserver ran on CPU throughout that entire interval. Serum's process call took 141.2 µs. The Linux transport worker was blocked awaiting the response. This is a synchronous Wine-server dependency, not evidence of slow synthesis or a host callback burst. The specific server operation monopolizing that interval was not identified.

The candidate adds a versioned, identity-bound shared-memory mailbox for existing audio request/reply frames. Lifecycle, state and supervision retain their existing socket/owner contract. Fixed delay and ordered sequence/epoch/position checks are unchanged. Every issued request retains its five-second failure deadline; missed presentation spans are counted while waiting. The callback still only copies into preallocated queues and never waits for either endpoint.

QPC's observed resolution was 100 ns. Linux monotonic/Instant correlation brackets were below 1 µs. Matching request/reply bounds limited the inter-clock offset uncertainty to 303.226 µs in the trace-only baseline and 198.366 µs in the scheduler baseline. Scheduler intervals use one Linux monotonic clock. Cross-clock durations were not obtained by assuming equal clock origins.

## Preserved comparisons and limits

Numerical observations are in `evidence/AP10/delivery-comparisons.json`. Native trace-only baseline source was 7f0bdb8 and Windows source c629a44; mailbox endpoints were ef1bebb. All used the same copied AP9 project, local audio and normally launched Bitwig. Perf targeted owned delivery/server threads; detailed histories were bounded and drained after processing.

- Socket baselines each counted two late 128-frame blocks at startup.
- The mailbox session's first missing output occurred only near request 137508, after roughly six minutes of processing. That event had 31.903 ms in reply preparation, 124.4 µs in Serum process(), and caused 19 late blocks. Scheduler capture had already ended; this event's blocking/CPU/scheduling cause is **unknown**. The mailbox session was not gap-free.
- Perf in that mailbox run began about 35 seconds after native startup. It does not provide a matched scheduler view of the original startup interval. Whole-session counters establish no earlier gap, not identical wineserver work.
- The untraced 256-frame session counted zero missing frames across 36,262 host blocks. Its 40-second local-audio/CPU window used 33.042 CPU-seconds for the supervised cohort versus 36.568 in the trace-only socket baseline. Tracing differs, so that approximately 10% reduction is provisional.
- Untraced 128 frames counted 3,840 missing frames across 74,068 blocks. It is not a recommended setting from this result.

The first mailbox candidate used C++ `sleep_for(50 us)`. Its trace shows approximately 1.06 ms wait increments, adding avoidable wakeup quantization. The implemented repair uses `NtDelayExecution` with the same requested 50 µs interval; the owner-thread comparison below measured the reduced quantization. A matched musical-load result for the final candidate remains incomplete. This is not a priority change or a new runtime.

Keep 512 frames as the established comparison/recommendation until subsequent actual results support a narrower claim. Hardware/converter latency is excluded; Moonlight is only the control surface.

## Commercial effect work

Actual FRAGMENTS 1.0.0.2925 SDK inspection declared stereo main input index 0, stereo sidechain index 1, stereo main output index 0, and one event input with zero declared channels. Both audio arrangements were SDK stereo (3). It reported 176 vendor samples, float32 support, no float64 support, and a zero tail value at inspection. These are metadata observations, not yet proof of audible effect behavior or actual tail duration.

The AP10 protocol adds an exact bus contract and bounded host transport context. Auxiliary audio remains represented but inactive; bus arrays retain their actual lengths and indices. Context comes from the DAW, including validity flags and chunk-adjusted sample/musical positions; absent information is not replaced by fabricated tempo. Vendor delay remains separate from bridge delay. The same generated descriptor mechanism preserves Serum's original native class and parameter identities.

Bypass produced visible track/master output; enabling the bridge subsequently silenced that path. The native failure now retains its first backend result without allocation, I/O or logging in the callback. AP10-specific admission codes distinguish extent/events, nonfinite input, contradictory silence flags and invalid context; existing AP7/AP8 return meanings are unchanged. The record is emitted after callback quiescence during teardown. The focused regression checks rejection before any chunk is queued, then checks in-place stereo input and host-context preservation across chunks.

The Windows pre-activation wait probe measured a 1,073,921 ns mean for `sleep_for(50 us)` and 111,696 ns for `NtDelayExecution(50 us)`, 32 samples each. This demonstrates reduced wakeup quantization on this Wine fixture, not a completed matched low-buffer result. Selected observations are retained in `evidence/AP10/effect-development.json`. After SSH access returned, the raw native and owner records verified the desktop transcription; the RMS transcription was corrected from 0.0016795 to the actual 0.00175946.

The d260dc2 diagnostic reproduced the failure with the same Windows binary and saved clip. Its first rejection was **0x104**, nonzero input under host `silenceFlags=3`; the worker still had fault 0. The owner again retired the Windows instance with confirmed containment. Context validation was not the cause.

The repair preserves every input sample and clears only silence hints contradicted by those samples. The SDK defines these flags as optional optimization hints, and its [silence tutorial](https://steinbergmedia.github.io/vst3_dev_portal/pages/Tutorials/How%2Bto%2Buse%2Bthe%2Bsilence%2Bflags.html) explicitly permits near-zero host buffers. No threshold, zeroing, resampling or precision conversion is introduced. The callback counts affected blocks/samples and retains the first sample bits and finite peak for off-thread reporting. Nonfinite samples still reach the existing rejection path. Instruments do not pay for this input-hint scan. Tests cover signed zero, subnormals, near-zero and ordinary nonzero input, partial-channel hints, bit preservation and NaN preservation for rejection.

The matched silence repair replay accepted 31,854 blocks with zero rejected callbacks and a clean close. Five callbacks contained 1,280 nonzero samples under silence hints, peaking at 1.095e-7. Two late startup callbacks (256 missing frames) remain counted. Windows retirement and containment were confirmed.

Bitwig Grain Mix controls at 0 and 1 produced different local audio: after alignment and fitting a scalar gain, the wet residual was 69.3% of wet RMS. These are unsynchronized monitor captures through an s16 device path, not sample-accurate latency measurements. The longer control session counted 1,792 missing frames over 215,184 blocks; a 31.328-ms Linux request-preparation interval caused one group of gaps, with no scheduler capture to distinguish its cause. It closed cleanly.

Recall failed: saving Grain Mix 1, quitting Bitwig and reopening through Applications returned the control to 0.5. Windows did service the final opaque GetState on its owner thread, but the digest stayed identical to initial state. Code inspection found that automation was sent only to IAudioProcessor::process; the Windows controller never received setParamNormalized. The [SDK hosting contract](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/API%2BDocumentation/Index.html) requires both destinations. The next candidate preserves ordered processor events and publishes bounded latest controller values for its existing owner loop. These counts are retained, not discarded as inaudible.

## Current Serum regression and decision

Normally launched Bitwig failed to activate the current Serum proxy before any audio callback. The bounded owner-thread diagnostic at native source 86d26cf records `activateBus(kEvent, kOutput, 0, true)`. Serum declares this main output bus with 16 channels. AP10 retains that SDK census and marks output events inactive, but Bitwig explicitly requests activation. Native and Windows activation policy reject event outputs; the process protocol and C ABI carry input events only. See `evidence/AP10/serum-bus-activation.json`.

This is an AP10 integration regression, not a vendor failure. AP9's proxy exposed only its hard-coded note input and audio output. Earlier AP10 Serum playback used that older bus shape, so it cannot qualify the final implementation. No output events were observed in this reproduction because processing never started. Accepting activation without a return path would silently discard any emitted events; deleting or relabeling the bus would contradict the current exact-bus requirement.

The recommended next scope is bounded plug-in-to-host events in the existing transport: declare supported SDK event types and payload limits, preserve bus indices/order and sample presentation relative to delayed audio, and specify explicit overflow/late-event failure handling. A deterministic return-event test must cover delayed note-off and variable blocks before actual Serum regression and matched 256/512 checks. This changes a currently absent real-time delivery contract; the draft returns that concrete scope decision rather than claiming completion or starting an unreviewed event model here.

## Final fixture disposition

Both failed Serum activation attempts closed without processing, and their Windows owners retired with confirmed containment and no error. All AP10 owners are stopped. Original Serum, FRAGMENTS and reference scanners/markers were restored byte-for-byte; the original FRAGMENTS session files were restored. The temporary native publication and trace/delivery flags were removed. Original Bitwig preferences/cache and the 512-frame setting were restored, as was PipeWire's original 256-frame minimum quantum. AP8/AP9 project hashes are unchanged. Private test projects/audio and raw evidence remain retained. Exact readback is in `evidence/AP10/cleanup.json`.
