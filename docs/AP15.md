## Product result

The bridge should disappear from the normal editor interaction. Bitwig’s editor action directly shows or focuses the exact detached vendor editor. Closing that vendor window retires the editor generation, not the plug-in. Reopening creates one new editor generation for the same DSP instance. Closing Bitwig’s editor view closes the vendor editor once.

## Source-grounded starting point

`native-vst3-proxy/source/vendor_panel.h` currently returns a fixed mapped X11 `IPlugView` that draws bridge-owned open/focus and close buttons. `attached()` maps the child and invokes `PanelOwner::panelOpen`; `onFocus(true)` forwards focus through the controller; `removed()` invokes `panelClose` and destroys the native child.

`native-vst3-proxy/source/commercial_controller.h` creates the panel and translates host lifecycle into native UI commands. `native-vst3-proxy/include/ap11_gui.h` defines the fixed command/status ABI, including `Open`, `Close`, `Focus`, `EditorStatus`, activation identity, target X11 ID and view epoch. `native-vst3-proxy/backend/src/gui.rs` and `queued.rs` own the mapped native UI session and generation.

On Windows, `windows-factory-probe/source/gui_channel.h` owns the mapped channel, `editor_session.h` services commands and publishes generation-aware status, and `vendor_view.h` owns the real VST3 vendor view and detached Win32 parent. `VendorView` already defers `WM_CLOSE` teardown out of the callback, preserves owner-thread operations, tracks open/close/focus counts, and supports plug-in-requested resize. AP14’s `environment_desktop.h` keeps the shared Wine/X11 desktop lifetime alive across scanner and DSP clients.

The panel therefore combines two different responsibilities:

1. the VST3/X11 object Bitwig requires and owns; and
2. a visible bridge control surface the musician should not see.

AP15 separates those responsibilities. It retains a host-correct native lifecycle delegate while removing the visible operational panel. It does not remove the VST3 view contract, embed the Windows editor, or make DSP depend on editor health.

## Primary engineering questions

## Completion threshold

AP15 is complete only when both deterministic and exact-fixture evidence show:

- one DAW action presents one vendor editor with no visible bridge panel;
- vendor close leaves the same DSP instance alive;
- DAW close closes the editor once;
- reopen creates one fresh generation;
- duplicate and stale requests are harmless;
- repeated cycles clean up all editor-specific ownership;
- editor failure is truthful and isolated;
- touched save/recall, automation, resize/popup and sibling behavior remain intact.

Do not call a hidden-but-still-clickable panel, an unmanaged floating process, a zero-size view Bitwig immediately discards, or a vendor window that cannot close/reopen cleanly a completed result.

## Local implementation checkpoint — Windows qualification pending

The implementation now separates native view tokens, vendor view epochs, activation serials and the existing processing generation. The native controller retains a bounded lifecycle record. A completed native removal emits one Close bound to that view and its acknowledged editor epoch; an opening with no acknowledged epoch may be cancelled only by the same native token. Retired results cannot validate or close a replacement. Editor epochs and native token/activation counters fail rather than wrap.

UI ABI **3** and mapped UI protocol **4** use a 608-byte message and 320-byte header. Both languages check the message layout/version; Rust checks the eight-byte ABI prefix before forming a full message reference. The separate close mailbox uses a bounded seqlock snapshot containing native token, expected editor epoch and command cutoff. The Windows owner never spins on an incomplete close snapshot. It admits only a supplied X11 parent advertising `WM_DELETE_WINDOW`, automatically requests the vendor editor after attachment, unmaps the host shell on MapNotify, and sends that parent's advertised close request when the vendor epoch retires. ## Source repair checkpoint — Windows capacity deferred

The source-hardening pass requested against `dd596b3e1031655e844d4ee7438d6c564f6db7e7` repairs seven ownership gaps before spending future Windows capacity. It does not qualify the experimental delegate on Bitwig. Previous observation, builds, failures and CI-start receipts remain unchanged under `evidence/ap15/`; this pass is recorded separately under `evidence/ap15/source-repair/`.

The controller now prepares an Open without advancing its lifecycle, and commits ownership only after the processor returns actual GUI-mailbox acceptance. Lifecycle command acceptance no longer depends on allocating a second reply message after the mailbox was already changed. Before Open, the controller reserves one retirement IMessage. Close needs no new message allocation; a refused send retains one exact pending command and controller reference. Disconnect/terminate refuse to discard it. The UI timer retries at most eight sends, then requests explicit GUI-only failure retirement with the reserved message. A host refusing even containment leaves removal refused and the single owner retained; it is not reported as cleanup. No retry, allocation, messaging or X11 operation enters audio processing.

XCB retirement now checks the send and flush before recording acceptance. Three failed transient sends are the maximum; an accepted send is never repeated. A flush failure after server acceptance is ambiguous delivery and stops resends. BadWindow/parent destruction, connection loss and other server refusal have distinct mechanical outcomes. Unmap failure triggers exact editor failure/retirement rather than pretending the shell is hidden. After one accepted WM_DELETE request, failure of the host to retire within 100 UI ticks is reported as refusal, with no duplicate request. XCB acceptance is not host application acknowledgement; actual Bitwig behavior remains pending. The bridge never destroys the host's parent.

Both native UI timers use an independent registration handler. Unregister refusal retains the exact registration and returns failed removal. The delegate retains its resources for retry. If a host releases a refused view, its destructor detaches the handler's callback before releasing the view; a small inert handler/loop receipt remains until unregister succeeds. It cannot call a destroyed delegate. Successful unregister releases the registration once, including hosts which do not retain handler references. A broken run loop which permanently refuses unregister can retain this bounded receipt; claiming full cleanup in that case would be false.

A processing/UI replacement records a monotonic retired-token watermark rather than erasing the old attached view's terminal projection. Old view A continues to observe `EditorFailed` and requests normal host-shell retirement; its removal acknowledges the already-retired old mapping locally. New view B uses a greater native token and a fresh activation context. Stale A Open, Close, Focus, status or scoped edit traffic cannot validate B.

Windows source now retains the exact HWND until `DestroyWindow` succeeds or `WM_NCDESTROY` confirms destruction. The callback clears GWLP_USERDATA even during intentional teardown, and intentional destruction is not `WindowLost`. Failed destruction retains ownership and refuses a replacement; retry does not double-count successful SDK `removed()` calls. The standalone vendor-access route still uses this mechanical view helper with its own admission/receipt and no DAW/project authority. These changes and their Windows fault-injection tests are **uncompiled and unrun** in this pass.

### Callback identity classification

| Windows-to-native traffic | Scope and retirement law |
| --- | --- |
| Begin, Value, End, GroupBegin, GroupEnd, Dirty, RequestOpen from an editor-installed handler | Immutable native view token and vendor epoch. A separate handler is installed before that editor is created. Close removes the view, completes accepted gestures, retires the handler and restores the instance handler. Cached old handler references become inert; queued old packets are refused by the native lifecycle. |
| The same callbacks from the persistent instance handler | Explicit zero/zero origin; legitimate controller-instance activity remains available without an editor. Gesture/group ownership cannot mix origins. |
| EditorStatus and Focus | Existing exact native token, editor epoch and activation identity. |
| RefreshBegin, Parameter, RefreshEnd | Instance scoped. A current editor's accepted restart may request a full controller refresh, but the resulting metadata/readback is instance data and is not stamped as an editor gesture. A retired handler cannot request a new restart. |
| Latency/topology restart notifications and host-originated Set | Existing instance policy, revisions and host ownership. No editor generation is invented. |

## Focused R2 — independent XCB operation outcomes

[Technical review 5160946354](https://github.com/kasselvania/Linux-VST-bridge/pull/86#pullrequestreview-5160946354) found that a rejected unmap incorrectly supplied the terminal guard for host-close delivery. The prior one-shot unmap fixture could also recover on a later unmap and overwrite that shared result, hiding the defect. Historical source-repair evidence above remains unchanged.

`VendorPanel` now retains separate unmap, SendClose and flush results. Parent disappearance and connection loss are independent terminal delivery facts; the diagnostic failure result does not authorize or suppress other operations. A rejected unmap stops further unmap attempts; three transient refusals exhaust its existing bound. Both report the exact editor failure once and still attempt checked WM_DELETE against a live parent. Only SendClose's own rejection/exhaustion, an already accepted send, ParentGone or ConnectionLost suppress subsequent host-close sends. The bridge never destroys the host-owned parent.

Checked X-server acceptance commits the one close delivery before the subsequent flush. An ambiguous flush therefore cannot cause a resend or erase accepted delivery. Application acknowledgement remains distinct; the existing 100-tick host-retirement refusal is unchanged. Controller command ownership, timer removal/retry, editor generations, Windows teardown, qualification, callback identity, state, transport and performance are unchanged.

The exact same final `panel.cpp` fixture fails with the reviewed `f359240` production header and passes with the repaired header. Persistent rejected unmap produces one exact parent/protocol WM_DELETE, one editor failure and no later duplicate. Normal host removal balances the editor close, timer, frame/loop and controller references; the surviving parent's event-mask readback proves the delegate XCB connection's selection retired. Additional focused assertions cover exhausted transient unmap and conclusive SendClose rejection. Existing transient send retry, connection loss, parent disappearance, ambiguous post-send flush, failed unregister, destructor-safe inert timer and no-child/control cases remain.
