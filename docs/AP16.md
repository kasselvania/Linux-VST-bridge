# AP16 — Causal 512-frame delivery reliability

## Implementation result — 10 September 2026

**One demonstrated preparation-stall class is repaired and the corrected manager/supervisor are installed for independent review. Matched trace-enabled playback and two trace-off confirmation intervals support the repair. Other gap classes remain. PR #89 is open and unmerged; this is implementation evidence, not merge acceptance.**

The selected recurring class is a native preparation stall during the saved note sequence with existing automation and both editors closed. Cold admissions were checked first: one of three trace-off admissions had LoFi misses and two were clean. Those cold results remain separate. The active phase reproduced 23–32 ms preparation tails with short vendor computation, including the exact capture below. [Completed baseline counters](../evidence/ap16/baseline-session-counters.json) retain unequal session lengths and are not a rate comparison.

### Exact missed request

[The bounded causal record](../evidence/ap16/causal-baseline.json) binds FRAGMENTS session `c9e3b5a0831359c3c989ee3e0b640c95`, processing generation 1, epoch 1, request **10742**, source position **2748928**, 256 frames, to producer callback **5370** and consumer callback **5371**. Both actual callbacks contain 512 frames, split into two 256-frame requests. The bridge presentation position is source position + 512 = **2749440**; `gap_position` names the missing source span.

| Stage | Elapsed |
| --- | ---: |
| Admission to worker | 43.440 µs |
| Worker preparation | **27.516972 ms** |
| Preparation to send | 17.400 µs |
| Send to observed reply | 1.011770 ms |
| Validation | 11.500 µs |
| Result publication | 6.960 µs |
| Available budget at admission | 10.675722 ms |
| Publication after actual presentation boundary | **17.932320 ms** |
| Vendor `process()` elapsed | 636.400 µs |

All Linux instants use CLOCK_MONOTONIC, with the existing observer's 400 ns start bracket and 370 ns end bracket retained. The presentation boundary is `137341527345454 ns`; publication is `137341545277774 ns`. Request 10741 was already published **8.441955 ms before 10742's admission**. Requests 10743–10747 waited behind 10742 and contribute to the six expired/missing chunks, **1,536 frames across three callbacks**. They are consequences of the first stall, not independent vendor slow cases.

The external bounded sampler caught native worker TID 87878 in **D / `do_get_write_access`** at four successive collection brackets. Its CPU, runnable-wait and scheduling-count values stayed unchanged; the LoFi worker continued. A period-1 `perf minor-faults:u` record using `--clockid mono` identifies the same session's `ap1.audio` page fault completing at `137341544199695 ns`, immediately before preparation completes. A second audio-page fault and status/mailbox write faults follow. The mapping was an ordinary ext4 MAP_SHARED file under the environment's session directory.

This assigns the selected excess elapsed interval to a filesystem journal wait reached by the bridge's backing-file choice. It excludes queue predecessors, explicit preparation sleeps, native CPU computation and vendor computation as the first cause. It does **not** identify the lower-level disk I/O owner or prove that every nanosecond of preparation belongs to one kernel suboperation. The source interpretation is Linux v6.16 [`do_get_write_access`](https://github.com/torvalds/linux/blob/v6.16/fs/jbd2/transaction.c#L880) and [`ext4_page_mkwrite`](https://github.com/torvalds/linux/blob/v6.16/fs/ext4/inode.c#L6145), combined with the actual on-device wait/fault evidence; no kernel source is copied into the implementation.

Windows QPC is a distinct clock. Its receive-wait interval begins after the previous request, so that interval also contains time when Linux has not submitted a request. It is not a measured Windows dispatch delay. Vendor elapsed is separately reported; the trace's coarse Windows thread-CPU readings and query overhead are not treated as precise vendor CPU.

### Installed storage repair

The Rust service owns `/run/user/UID/linux-vst-bridge`, requires tmpfs and a private exact ownership marker, and creates one new private directory per DSP session. It checks SO_PEERCRED and the actual peer's mounted device/inode before exposing a native binding. There is no disk-backed fallback. The native binding supports this supplied session location. The pinned Windows host instead requires its exact C: handshake location. The supervisor preserves that requirement and exposes only the native-created `ap1.control`, `ap1.audio`, `ap11.ui`, `ap12.status` and optional `ap10.delivery` files there as exact symlinks into the private RAM session. It validates ownership/type and refuses existing aliases before publishing them, then opens the Windows gate. No callback, mailbox, protocol, precision, delay, state or editor code changes.

The existing durable prefix session record still owns `owner.json`; reports and retirement receipts remain in the manager store. The supervisor gives the keeper and audio child only the fixed bridge-owned runtime directory through the existing pressure-vessel filesystem interface. Ready/gate paths remain under the existing durable `C:\bridge\sessions\SESSION` contract; those admission-only writes do not back the hot mappings. After both Windows containment and native release, exact memory-directory identity is checked again, the transient files and durable session record are removed, and only then is retirement acknowledged. Failed physical removal does not produce a successful receipt. A binding exposed before launcher failure retains an unresolved lease and blocks further admission instead of forgetting native ownership.

Inspection and standalone vendor access retain their existing persistent session directories. Revision-7 profiles, host/native/module artifacts, revision-3 rollback targets and vendor state remain unchanged. tmpfs removes this journaled backing mechanism; it does not promise unswappable memory or freedom from other page faults and scheduler/vendor delays.

## Prepared decision

AP16 activates [issue #72](https://github.com/kasselvania/Linux-VST-bridge/issues/72) from integrated `main` at `510d88bd89adbf8b101140907f27dc9885af9f25`.

The selected result is deliberately narrower than “fix all audio performance”:

> Under the ordinary AP15 revision-7 Pure LoFi → Efx FRAGMENTS installation at 512 added frames per proxy, reproduce one residual delivery-stall class, assign the missed request to a real owner, repair its demonstrated project-owned cause or provide a truthful bounded external mitigation, and show a matched before/after result without changing timing semantics.

AP15 is complete and must not be reopened. Revision 7 remains ordinary verified policy, revision 3 remains exact rollback, direct detached editors remain the intended editor lifecycle, and 512 remains the supported/recommended starting point. The opt-in 256 setting remains unqualified.

Repository visibility does not change project ownership. `COPYRIGHT.md` and `CONTRIBUTING.md` remain authoritative for licensing and contribution terms; AP16 is a technical slice only.

## Current evidence, correctly bounded

AP13 established that one serious delivery failure was caused by a read-only state capture occupying the Windows owner while audio waited. Protocol v12 repaired that exact serialization and preserved independent state/failure meanings. It did not explain every prior tail.

The accepted AP15 ordinary revision-7 smoke retained these stopped/pre-note counters:

| --- | ---: | ---: | ---: | --- |
| Pure LoFi | 3 | 1,280 | 0 | clean |
| Efx FRAGMENTS | 1 | 512 | 0 | clean |

The broader AP15 qualification campaign retained additional gap groups during musical/editor use. These records prove missed presentation boundaries; they do not, by themselves, prove that every interval was audible or share one cause.

Existing evidence contains very different elapsed shapes:

- multi-millisecond callback-to-worker queue delays with small native preparation time;
- Windows reply intervals where vendor process time accounts for most of the service;
- historical 24–31 ms native preparation/publication intervals with incomplete scheduler attribution;
- startup requests admitted with less remaining budget than their ordinary service requirement.

AP16 must choose and reproduce one class before changing code. Do not average unlike classes together.

## Current instrumentation

### Native request and gap correlation

`native-vst3-proxy/backend/src/queued.rs` records request lifecycle points and owns the `ap3-transport` worker. `native-vst3-proxy/backend/src/observer.rs` receives fixed-capacity observations outside the callback and correlates retained gaps to requests by epoch and sample range.

The current `Trace` carries:

- epoch, sequence, sample position and frame count;
- callback ancestry and previous control activity;
- callback admission (`queued`);
- worker start;
- native preparation complete;
- send complete;
- reply observed;
- validation complete;
- output publication complete;
- Windows vendor-process elapsed time;
- trace arming and clock-bracket information.

The observer stores only bounded windows and explicitly counts dropped jobs, samples and unretained gaps. That is the right ownership shape and should be extended rather than replaced.

### Existing aggregate interpretation

`native-vst3-proxy/backend/src/performance.rs` reports fixed histograms for queue, prepare, send, reply, validation, publication, total admission-to-publication, Windows process and the correlated non-plug-in residual. It retains exact maxima and top slow requests.

Those values identify elapsed stage concentration. They cannot alone tell whether a 7 ms queue interval was:

- worker execution on earlier work;
- runnable delay;
- sleeping/backoff;
- scheduler preemption;
- a page fault;
- another process-owned dependency.

Similarly, Windows `process_ns` is elapsed around vendor `process()` unless a new source-grounded CPU counter is added; do not call it CPU time without verifying its collection law.

### Supervisor and platform evidence

`bridge-manager/runtime/session.py` owns process identity, environment/session descendants, optional trace handoff and cleanup receipts. Prior bounded `perf sched` observations exist, but AP16 must correlate any new scheduler capture to the exact current request and current revision-7 product rather than infer from old thread names.

## Recommended first investigation

Start with the smallest recurring **cold admission / pre-note** class because it already appears in the final ordinary AP15 smoke and can be exercised without conflating a complex musical gesture. Establish whether the same shape repeats under the exact revision-7 installation.

If it does not repeat reliably, move to one bounded active-note or automation phase. Do not immediately combine startup, editors, automation, save and device removal into one campaign.

A proportionate sequence is:

1. Record a trace-off baseline with exact gap counters and normal CPUWeight.
2. Enable the existing bounded correlated trace and identify the first matching missed request.
3. Add the smallest non-callback evidence required to distinguish worker CPU from runnable/off-CPU/blocking time.
4. If Windows reply dominates, distinguish host dispatch from vendor `process()` and result publication before changing Linux scheduling.
5. Reproduce the selected mechanism deterministically through a production helper or narrow fault-injection seam.
6. Repair that mechanism.
7. Run matched trace-enabled before/after and trace-off confirmation.
8. Retain all other observed classes as unresolved rather than broadening the claim.

## Evidence ownership requirements

The final evidence should make one request readable as an ordered causal record, for example:

```text
callback admitted request N with X microseconds remaining
worker began after Y microseconds
worker consumed A microseconds CPU and B microseconds elapsed before send
Windows received/dispatched after C
vendor process consumed D elapsed / E CPU where measured
reply/result became visible after F
Linux validated and published after G
callback presentation boundary occurred at H
request missed by J
```

Use exact clock-domain labels and correlation uncertainty. Do not subtract counters from unrelated clocks as if they shared an epoch.

Retain a bounded negative/control result showing that the diagnostic mechanism itself did not create the stall class. Raw audio and proprietary state remain unretained.

## Product invariants during repair

- The callback remains nonblocking and allocation-free under its accepted contract.
- Output is published only for its exact epoch/position; late output does not become future audio.
- Events and parameter points keep their exact sample offsets and ordering.
- Editor, state and audio failures remain distinct.
- One instance's repair or failure does not poison its sibling.
- Instance/process cleanup remains positively owned.
- Ordinary revision-7 profiles and stable processor/controller IDs do not change merely because diagnostics or scheduling mechanics change.
- If native or Windows artifact bytes change, use the established immutable candidate/profile/publication and independent-review transition rather than silently replacing revision 7.

## Tests expected from the selected mechanism

Do not write every possible performance test in advance. Once the cause is selected, use production helpers to cover the exact law. Likely required seams include:

- delayed worker admission without lost requests;
- delayed or spurious wakeups;
- worker backlog and bounded queue behavior;
- delayed Windows result and exact timeout/presentation handling;
- no stale output after a miss;
- no event/state/editor regression;
- bounded trace overflow and trace-off equivalence;
- cleanup after a request remains unfinished or late.

Preserve all existing native, Windows, manager, state-delivery, direct-editor and proof-policy lanes.
