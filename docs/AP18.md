# AP18 — Arturia Software Center to Pigments

## Decision

AP18 closes the first official vendor-managed installation vertical. The bridge already runs and manages exact installed Arturia VST3s; it does not yet own the path by which a user obtains, authorizes, installs, discovers, and publishes one through Arturia's normal software.

The selected result is:

```text
official Arturia Software Center installer
→ managed Arturia environment
→ real ASC application and user-owned account flow
→ Pigments download and installation
→ exact automatic discovery and registration
→ reversible Pigments candidate publication
→ real Bitwig qualification
```

This is intentionally one end-to-end product slice. Internal gates may fail honestly, but AP18 should not be split into disconnected “ASC launches,” “files appeared,” and “Pigments maybe works” milestones that never complete the user journey.

## Existing code to reuse

### Environment ownership

`bridge-manager/src/main.rs` already creates/imports exact persistent environments and verifies their pinned runner. The accepted Arturia environment is a vendor-family state container rather than a disposable one-process prefix.

### Installer launch

The current CLI already exposes:

```text
linux-vst-bridge install ENV_ID INSTALLER_PATH SHA256
```

It canonicalizes and verifies the installer, writes a private installation job, and launches the supervisor through a bounded user systemd unit.

`bridge-manager/runtime/session.py::install` currently:

- obtains the environment operation lock;
- verifies the installer and runner files;
- launches the installer through the exact Proton runner;
- tracks the launcher and descendants;
- bounds captured stdout/stderr;
- enforces a one-hour operation deadline;
- contains owned processes on exit/failure;
- writes a private report with launcher result, cleanup, and diagnostics.

That is useful but insufficient for ASC. It treats installation as one foreground process whose completion ends the operation. ASC is a persistent companion application that may start helpers and later run long downloads/installations after its initial installer has exited.

### Vendor application access

The service already supports a separate vendor-access owner for one plug-in editor. AP18 may reuse its environment exclusivity and ownership ideas, but ASC is not a plug-in editor and must not be forced through a fake VST3 class request.

### Module inspection and publication

The manager already verifies exact modules inside the environment, runs supervised Windows factory/class inspection, derives registrations, builds native proxy artifacts through descriptor-owned routes, publishes immutable revisions, and restores exact parents.

AP18 should compose these accepted pieces. It should not create a second independent environment registry, scanner, publisher, or process owner.

## New product records

Private representations are implementation choices, but the following meanings need one canonical Rust owner.

### Installer artifact

At minimum:

```text
installer id/digest
original filename
private retained path
byte size
file type
available publisher/signature facts
operator source assertion
admitted environment
first-use timestamp
```

The installer bytes remain private and uncommitted.

### Vendor application

At minimum:

```text
vendor application id
vendor family
exact environment/revision
installed executable identity
application/version metadata
known helper/service identities
launch policy
observed data/cache/download/resource roots
last operation/result
```

No arbitrary executable path supplied at launch time may become vendor-application authority.

### Vendor operation

The manager must distinguish observable states such as:

```text
prepared
launched
waiting_for_user
running
product_downloading
product_installing
completed
failed
cancelled
cleanup_unconfirmed
```

Do not invent a state solely from window title text or launcher exit. Unknown is a valid result.

### Installed vendor product observation

For Pigments, retain non-secret facts such as:

```text
product identity/name
observed ASC status
installed VST3 module path/digest
factory/class census
standalone executable identity where present
resource/content/preset roots
safe registry/file manifest deltas
authorization posture: confirmed/required/unknown, without payload
```

An observation becomes a bridge compatibility claim only through a separate profile and qualification result.

## Installer intake

The operator has placed unopened ASC installer file(s) in `$HOME/Downloads` on the Steam Deck.

Intake must be bounded:

1. Enumerate only plausible regular files in the immediate Downloads directory; do not recursively census unrelated personal files.
2. Preserve original filename and bytes.
3. Calculate SHA-256 and size.
4. Identify PE/MSI/container type without execution.
5. Read Authenticode publisher/signature facts when supported; inability to validate a signature must be reported rather than silently converted to trust.
6. If multiple distinct ASC installers remain plausible, stop before execution and present their bounded identities for operator selection.
7. Copy the selected exact file to a private content-addressed manager artifact location with restrictive permissions.
8. Verify the copy byte-for-byte before use.

Do not upload, commit, unpack into the repository, rename or delete the original, or fetch a substitute installer from an arbitrary URL.

## Pre-install transaction

ASC will mutate the existing Arturia environment. Before execution:

- close Bitwig;
- require zero DSP leases and no pending publication/qualification transaction;
- require no unresolved vendor/install operation;
- read current service/keeper and environment health;
- activate accepted ordinary revision 10 once and verify physical publications;
- retain exact LoFi/FRAGMENTS modules, profiles, publications, external IDs, resource roots, authorization posture, and protected-project hashes;
- measure environment size, free storage, and expected temporary headroom;
- capture an allowlisted filesystem and safe-registry baseline;
- create a private, non-running rollback snapshot or exact backup of every root ASC is allowed to modify.

The backup is recovery material, not another runnable authorized environment. Do not launch it or treat it as a second licensed device.

If full-prefix copying is selected for rollback, account for Pigments/ASC download size and disk pressure before starting. Prefer a filesystem snapshot/reflink or bounded changed-root backup when available and trustworthy.

## Installing ASC

Use the current installer command as the starting owner. Extend it only where the real installer proves necessary.

Success requires more than launcher exit zero:

- expected ASC executable exists in the exact environment;
- executable identity and installed version are retained;
- required helpers/services are identified;
- no unresolved installer process remains;
- relevant before/after roots are recorded;
- the application can be launched again without the installer;
- rollback can identify what the transaction changed.

Keep ASC and vendor infrastructure in the same Arturia environment as LoFi, FRAGMENTS, and Pigments unless actual incompatibility demonstrates a need for a new environment family.

## ASC application owner

Implement a narrow product-owned companion-application route rather than an arbitrary Wine command.

The manager should be able to:

```text
asc status
asc launch-or-focus
asc stop-owned-operation   # only where safe and necessary
asc rescan-products
```

Exact CLI spelling is an implementation detail. The meanings are not.

Requirements:

- launch only the registered exact ASC application in the registered exact environment;
- preserve foreground UI and modal children;
- retain process-tree ownership by PID plus start identity privately;
- distinguish application UI, vendor services, and active product-install helpers;
- avoid killing helpers required for a completed installation or future authorization;
- block conflicting environment mutation/inspection and live DSP as required by existing laws;
- survive launcher handoff when another helper becomes the visible/continuing owner;
- permit normal close and later relaunch;
- report unresolved ownership honestly.

Do not make ASC an environment keeper replacement. The existing keeper has a different job and loads no vendor application.

## Account interaction

Credential handling is a hard boundary:

- the user interacts directly with ASC;
- the agent may position or focus the real application but must not inspect secret text fields, clipboard contents, cookies, tokens, account emails, serials, or license payloads;
- no screenshot or committed log may expose account identity or authorization material;
- pause at login, MFA, consent, purchase, license choice, or other sensitive actions;
- resume only after the operator states the action is complete.

The system may observe non-secret resulting application/product state, but it may not reverse-engineer or automate Arturia's private service protocol.

## ASC usability and manager UI decision

The real ASC UI is the preferred product surface for account, catalogue, download, installation, and activation.

Do not build a manager UI merely because a UI is planned eventually.

A bridge-owned frontend is justified only if a demonstrated problem prevents the flow, such as:

- ASC cannot be found or relaunched reliably;
- its window opens behind other applications and cannot be recovered through normal activation;
- launcher exit loses continuing download/install ownership;
- the user cannot tell whether bridge-owned discovery/publication has caught up;
- a rescan or recovery action has no usable existing surface.

The minimal surface may expose:

```text
Arturia Software Center: installed / running / needs attention
Launch or focus
Current vendor operation
Detected products
Rescan
Pigments: installed / candidate / published / failed
Exact non-secret error and next action
```

It must read canonical manager state. It may not become a second store, login form, license service, or profile authority.

## Arturia paths and content

Do not assume ASC installs only a `.vst3` file. Observe at least:

- VST3 module/bundle;
- standalone Pigments application;
- shared Arturia Resources;
- factory presets, samples, and databases;
- per-user configuration/preferences;
- program-data and download cache;
- helper/service data;
- authorization posture.

Keep vendor paths stable and Windows-native inside `C:` first. External Linux bind paths can introduce drive/remount and graphics/resource behavior that the project has not qualified. Use them only if real capacity or compatibility evidence requires them.

Do not index or commit paid content. Product/resource discovery retains identity, count, bounded metadata, and roots—not transferable content.

## Post-install discovery

A generic “find Pigments.vst3 by filename” is insufficient.

The manager should:

1. compare the allowlisted pre/post installation manifests;
2. identify new or changed VST3 module candidates;
3. verify each candidate is inside the exact environment;
4. run the existing supervised factory/class census;
5. select the Pigments class from exact factory/class metadata;
6. retain module digest, class ID, vendor, name, version, role, subcategories, buses, parameters, state capability, latency, and editor facts available from the scanner;
7. refuse ambiguity or multiple plausible classes until resolved;
8. derive the source-owned native descriptor and stable external IDs;
9. build an exact native proxy;
10. form one immutable `review_candidate` profile.

The profile should contain no installer command, ASC executable command, credential path, mutable download root, or user-entered class ID.

## Capacity-policy extension

AP17's class limits are an exact LoFi/FRAGMENTS fixture, not a generic two-entry maximum and not a universal Arturia table.

Pigments requires a versioned policy extension that preserves:

- service workers 16;
- global DSP envelope 6 unless new evidence explicitly changes it;
- LoFi maximum 3;
- FRAGMENTS maximum 4;
- native-image hard ceiling 4;
- maintenance ownership;
- exact over-capacity refusal.

Begin Pigments at a class limit of one for qualification. Do not rerun the AP17 maximum matrix or claim a six-instance Pigments project. A later capacity slice may broaden the class envelope.

## Candidate publication

Use one sealed AP18 qualification route for the exact Pigments candidate. It may accept a private package location, but every artifact/profile/module/class/environment/parent identity must be compiled or otherwise closed by source-owned policy before mutation.

It must not accept arbitrary:

- profiles;
- module/native/host paths;
- hashes;
- class IDs;
- environment IDs;
- commands;
- downloads;
- vendor application executables.

LoFi and FRAGMENTS ordinary revision 10 remain active and unchanged. Pigments begins as engineering-only authority and is restored/unpublished after the campaign pending independent review.

## Pigments qualification scope

The first qualification asks whether Pigments is a usable exact VST3 instrument through this bridge—not whether every Pigments feature is supported.

Required real checks:

- exact candidate is discoverable in Bitwig;
- one instance admits and processes notes;
- local output is nonzero;
- real editor opens directly, navigates, resizes, closes, and reopens on the same DSP instance;
- one factory preset loads through Pigments' own browser;
- one real parameter gesture reaches Bitwig as begin/value/end;
- host automation replays into sound and UI;
- protected project save/reopen restores intended preset and visible state;
- opaque state capture/restore is classified truthfully;
- one accepted Arturia sibling remains healthy alongside Pigments;
- Pigments removal retires only its own editor/process/transport/state;
- normal Bitwig quit leaves positive ownership cleanup.

Retain the exact Pigments-reported latency, buses, sample-size support, parameter count, state size, editor scaling/rendering limitations, and delivery gaps observed.

Not required for AP18:

- every preset;
- every synth engine;
- MPE qualification;
- sidechain/external audio input;
- float64;
- exhaustive popup/file-dialog behavior;
- multiple Pigments instances;
- 256 frames;
- universal Arturia compatibility.

## Existing products and vendor updates

ASC can update existing products or shared resources. The operator should select only Pigments.

After installation, compare LoFi and FRAGMENTS exact modules and critical shared roots against baseline. If ASC changed them despite operator selection:

- retain the exact private delta;
- do not publish changed bytes under revision 10;
- determine whether the change is shared-resource-only, module update, authorization change, or another vendor mutation;
- restore baseline if the change breaks accepted projects;
- create a separate immutable candidate/update transition only when needed.

A successful Pigments installation must not silently invalidate existing accepted Arturia projects.

## Failure and recovery

At each phase, preserve a useful stopping point:

- installer rejected before execution;
- ASC install partial;
- ASC launches but sign-in is blocked;
- authorization unavailable;
- Pigments download interrupted;
- download complete but installation failed;
- module installed but census fails;
- census succeeds but bridge feature unsupported;
- candidate publishes but Bitwig fails;
- project works but cleanup or state fails.

Do not erase partial vendor state until its ownership and recovery implications are understood. Prefer the vendor's own resume/repair/uninstall mechanism where available. The private baseline snapshot remains the last-resort exact rollback.

## Validation

Run tests for changed owners only, plus the normal final-head lanes.

At minimum when corresponding code changes:

```text
cargo test --manifest-path bridge-manager/Cargo.toml --locked
cargo clippy --manifest-path bridge-manager/Cargo.toml --locked --all-targets -- -D warnings
python3 -m unittest discover -s bridge-manager/runtime -v
```

Run native backend/audio-client/CMake tests when Pigments proxy or native startup code changes. Run Windows host CI when Windows source, Windows tests, shared ABI, scanner behavior, or host inputs change.

Use actual ASC and Pigments evidence for claims synthetic tests cannot establish. Do not repeat AP17's six-device, reboot, service-loss, and capacity campaigns.

## Final handoff

The implementation PR should report:

- exact final head, parent, and tree;
- selected installer metadata and private artifact identity, without bytes/path disclosure;
- exact environment and rollback posture;
- ASC installation and application ownership;
- user-owned authorization result without secrets;
- actual Pigments product/module/resource observations;
- automatic census and profile derivation;
- native/Windows/profile/publication identities;
- Bitwig editor/preset/audio/automation/state/save-reopen/sibling/removal result;
- existing-product preservation;
- local and hosted validation;
- final installed physical state;
- failures, limitations, and nonclaims;
- confirmation that 512 remains recommended and 256 unqualified.

## Post-login blocker: bounded stopping point

The three registered launches all ended with launcher exit 5 and positive
cleanup after the operator reported that the library window did not appear
following sign-in. Exit 5 identifies the launcher result; it does not establish
an ASC UI error, invalid credentials, a crash, or which process caused failure.

The installed vendor shortcuts specify the executable directory as their working
directory, with no arguments. Commit `a3ab31c907676c6334e0b0c862e0047d0ecee56f`
makes the companion launch match that contract. The actual main process used the
correct directory, but the third attempt still failed identically. This corrects
the launch contract; it is not a fix for the observed post-login failure. A
deterministic command-shape test, 24 Linux runtime tests, 53 manager library and
8 binary tests, clippy and the Linux release build passed. Those results do not
qualify ASC or Pigments.

The bounded check inspected main/agent PE imports, file versions, explicit Wine
version settings, ASC-specific accessibility settings, vendor-named service
configuration and matching coredump availability. It did not identify the
failure owner. The current owner discarded 529 diagnostic bytes on each attempt,
so their contents cannot be recovered from these receipts. No account logs or
authorization databases were inspected. Retrying login without fixing that
diagnostic gap would not test a new hypothesis.

Further retries are stopped for a focused technical handoff. The next missing
observation is the main/agent/launcher exit sequence and a non-secret failure
origin at that boundary. Capture only allowlisted process/runtime facts before
asking the operator to repeat sign-in. Do not infer a runtime defect, delete
preferences, change authorization or reinstall from these results.
