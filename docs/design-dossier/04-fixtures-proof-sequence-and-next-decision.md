# 13. Flagship fixture pressure

## 13.1 Serum 2 — first real plug-in

Serum 2 is an excellent first commercial target because it combines ordinary VST3 expectations with meaningful product pressure:

- current 64-bit Windows VST3 delivery;
- one of the best-known modern software synthesizers;
- substantial graphical editor and resize behavior;
- factory presets, wavetables, and sample/noise content;
- user preset/content workflows;
- MIDI and automation-heavy use;
- state/project recall importance;
- Xfer-owned browser authorization and documented offline authorization;
- a distinct Splice Rent-to-Own channel with companion-app recurring verification.

The fixture must declare which authorization class is tested. The preferred first proof is an Xfer-owned/lifetime route if that is the maintainer's lawful license, because it isolates the bridge from Splice's recurring companion-app requirement while still testing a real browser/offline-capable activation. If the maintainer's actual license is active Rent-to-Own, that becomes part of the fixture rather than something hidden.

### Serum 2 capability ladder

A Serum 2 claim should advance explicitly:

```text
installer observed
module discovered
factory/classes censused
native proxy discovered by Bitwig
component/controller lifecycle established
audio and MIDI correct
automation identities stable
state round-trip correct
project save/reboot/reopen correct
editor detached and usable
popups/menus/drag-drop characterized
presets/content resolve
license behavior characterized
stress and crash recovery retained
```

No earlier rung implies a later one.

## 13.2 Kontakt — hostile systems test

Kontakt is valuable precisely because it is not “just another DLL.” The pressure system includes:

- Native Access installation, activation, and update ownership;
- account login and internet requirements;
- separate application, download, and content paths;
- large libraries on internal or external storage;
- locate/relink workflows;
- product serials and third-party libraries;
- full Kontakt versus Kontakt Player behavior;
- licensed versus unlicensed library browser behavior;
- legacy products and historical library formats;
- library updates that may no longer load in older Kontakt versions;
- missing-content recovery and project recall.

Kontakt success must therefore name an exact matrix:

```text
Kontakt major/minor build
Native Access major/minor build
license/edition
representative NI library
representative licensed third-party library
representative unlicensed/full-Kontakt library, if lawfully owned
content filesystem and path
runner/environment/profile
Bitwig build and installation mode
```

The first Kontakt proof should not attempt the entire ecosystem. It should choose one exact small library and one external content-root relocation case.

# 14. Dependency-ordered development proof sequence

This is not a calendar, release sequence, or promise. It is the actual technical dependency order needed to avoid building a polished manager on an unproved bridge or a clever bridge around an unmanageable product.

## Step 0 — repository and design seed

Establish authority, product laws, language boundary, exact research basis, fixture cards, evidence rules, and no-active-slice posture.

**Result:** this dossier package. No compatibility claim.

## Step 1 — exact host and commercial-fixture reconnaissance

On the real Steam Deck + Bitwig Flatpak fixture, capture:

- host/runtime/sandbox facts;
- lawful Serum 2 installer and license channel;
- installer windows/processes;
- authorization path;
- exact installed VST3 module and content roots;
- current behavior under a deliberately selected experimental runner;
- sanitized blockers.

This step may use manual launch tooling. It does not yet build the bridge.

**Why first:** it prevents designing an installer/authorization system for an imaginary Serum path and prevents mixing bridge failures with license or content failures.

## Step 2 — native host probe

Build the smallest native Linux VST3 bundle that Bitwig Flatpak discovers and instantiates. It exposes deterministic metadata and diagnostics but does not represent Serum.

**Why:** prove the DAW-facing build, bundle, path, sandbox, dependency, and teardown seam independently.

## Step 3 — Windows VST3 factory census

Build a supervised Windows scanner under the selected runner that loads an open reference module and Serum 2 separately and produces a normalized factory/class/interface census.

**Why:** exact class identity and VST3 object coverage precede proxy publication.

## Step 4 — mapped native proxy factory

The native proxy presents cached exact factory/class metadata to Bitwig and launches the Windows host for lifecycle calls. No real-time audio claim yet.

**Why:** prove native-to-Windows identity and reentrant control protocol without hiding audio problems inside it.

## Step 5 — component/controller/state lifecycle

Support the exact VST3 component and edit-controller lifecycle required by the fixtures, including state get/set and deterministic reference-fixture round-trip.

**Why:** VST3 is not a single process callback. Project safety starts before audio.

## Step 6 — bounded audio and event transport

Add preallocated shared-memory audio buffers, bounded synchronization, event/parameter transport, buffer/sample-rate changes, activation/deactivation, silence flags where required, and deadline failure posture.

Prove an open deterministic module first, then Serum 2 as the first commercial instrument.

## Step 7 — Bitwig project recall

Test Serum 2 parameter automation, state, presets, Bitwig save/close, full process stop, Steam Deck reboot, and reopen. Record exact sound/state comparison and content resolution.

**Why:** this is the first moment the product begins to be musically useful rather than technically impressive.

## Step 8 — detached editor and popup constitution

Implement a supervised detached editor with correct thread affinity, focus, sizing, popups, menus, keyboard, and failure isolation. Characterize drag-and-drop separately.

## Step 9 — managed install/publish vertical

Replace manual fixture setup with a manager transaction:

```text
select Serum installer
-> create Xfer environment
-> run installer
-> perform authorization handoff
-> scan
-> generate/publish proxy
-> Bitwig rescan guidance
-> first launch
```

## Step 10 — compatibility profile and rollback

Move exact Serum-specific runtime/dependency/editor/install facts into a reviewed versioned profile. Stage a runner or plug-in update and prove rollback without losing the known-good route.

## Step 11 — Flatpak production packaging experiment

Compare user VST3 path, Linux Audio extension, and narrow host-broker shapes using the same proxy/host protocol. Select from evidence rather than convenience.

## Step 12 — multi-instance, process grouping, and stress

Exercise multiple Serum instances, different Bitwig sandbox modes, buffer sizes, sample rates, project loads, editor churn, crashes, and host cleanup. Establish process-group law.

## Step 13 — preset/content organization

Index Serum factory/user content without rewriting it; add user metadata; test content relocation and missing-content repair through supported mechanisms.

## Step 14 — second ordinary plug-in family

Choose a different vendor and graphics/authorization shape to prevent overfitting to Serum.

## Step 15 — Kontakt hostile vertical

Introduce Native Access and one tightly scoped Kontakt/library matrix. Treat vendor manager, large content, and legacy behavior as distinct owners.

## Step 16 — CLAP and additional DAWs

Only after the VST3 product boundary is stable, add the CLAP native/Windows bridge and another native Linux DAW through shared core contracts rather than copy-pasted implementations.

# 15. Acceptance scenarios

## 15.1 First-use success

A user on the reference Steam Deck installs the application, selects Bitwig Flatpak, chooses their lawful Serum 2 installer, completes Xfer authorization, and sees Serum 2 in Bitwig without terminal commands. They play notes, automate a parameter, choose a preset, save, reboot, and reopen with the same state and content.

## 15.2 Authorization popup

Serum opens a browser authorization flow. The manager keeps the correct environment session alive, opens the browser, routes the documented return, avoids logging secrets, confirms vendor-reported success, and later starts Serum without reauthorization.

## 15.3 Recurring-license distinction

An active Splice Rent-to-Own fixture is clearly marked as requiring Splice Desktop and recurring online verification. The product does not present an Xfer-owned compatibility result as proof of the Splice route.

## 15.4 Scanner crash

A malformed reference module crashes during class enumeration. The scanner dies; the manager quarantines the module, records the exact stage, cleans children, and Bitwig remains unaffected.

## 15.5 Audio host crash

The Windows host for one plug-in instance is terminated during playback. Bitwig remains running, the callback follows declared failure output, the instance is marked failed, other process groups remain healthy, and no orphan host survives.

## 15.6 Editor crash

The editor process/window path fails while Serum audio continues. The user closes or restarts the editor and can still save the project.

## 15.7 Runner regression

A new audio runner causes Serum's editor to fail. The manager reports the changed runner, returns the environment to its prior runner, and restores the verified editor without reinstalling Serum.

## 15.8 Plug-in update changes metadata

A Serum update changes a parameter or interface census. The manager does not silently replace the active build. It shows the difference, tests state recall, and permits rollback.

## 15.9 Missing content

A user moves Serum content or a Kontakt library. The system identifies the missing content root, distinguishes it from authorization or binary failure, and invokes the supported locate/repair route.

## 15.10 Flatpak runtime transition

Bitwig changes its Freedesktop runtime branch. The product detects that an extension build no longer matches, keeps user environments intact, and republishes/rebuilds only the Linux-facing package required by the new runtime.

## 15.11 Unsupported driver

A vendor installer requires a Windows kernel driver or unsupported dongle path. The product stops with a known-incompatible or owner-blocked classification rather than claiming installation success.

## 15.12 Support bundle

The user exports diagnostics. The bundle contains exact versions, redacted process and protocol evidence, timing aggregates, profile identity, and error receipts—but no plug-in binary, full prefix, account data, or license payload.

# 16. Pre-mortem

Assume the project failed. Likely causes include:

## 16.1 We built a better bridge but not a better product

Audio works, but users still install Wine, edit prefixes, run synchronization commands, and search forums. Prevention: manager and recovery experience are first-class design, not post-bridge polish.

## 16.2 We overfit to Serum 2

The architecture encodes one module, one editor, one authorization route, and one content layout. Prevention: exact fixture cards, open deterministic fixtures, a second ordinary vendor before Kontakt, and profiles rather than hard-coded vendor logic.

## 16.3 We made Kontakt the architecture

The first year disappears into Native Access and legacy libraries before basic VST3 audio is proven. Prevention: Kontakt remains a later hostile vertical.

## 16.4 We trusted a single blocking RPC channel

Reentrant VST3 host/plugin/editor callbacks deadlock. Prevention: protocol design explicitly supports recursion, thread affinity, and multiple in-flight call lanes before audio claims.

## 16.5 We called shared memory “real-time safe”

Control locks, page faults, allocation, or process scheduling still miss deadlines. Prevention: callback-path instrumentation, pre-faulting/preallocation, bounded waits, stress matrices, and explicit failure output.

## 16.6 We chased embedded windows too early

Months are spent on X11/Wayland reparenting while detached editors could have delivered usability. Prevention: detached correctness is first editor acceptance.

## 16.7 We tied the product to Steam

The Steam Deck works, but Ubuntu/Fedora users need Steam and game launch entries. Prevention: runner distribution and launch are project-owned; Proton is a source/basis, not product authority.

## 16.8 We relied on Bitwig's broad current Flatpak permissions

A manifest update breaks host launch or path visibility. Prevention: exact host probes, extension/broker alternatives, and no permanent claim from current permissions.

## 16.9 We created one giant prefix

Vendor updates corrupt unrelated plug-ins and support cannot assign ownership. Prevention: environment families with explicit sharing policy and transactional revisions.

## 16.10 We leaked license state

Support bundles or Git evidence contain account/activation data. Prevention: allow-listed receipts, sensitive-environment classification, redaction tests, and no full-prefix exports.

## 16.11 We inherited GPL code without choosing that product model

A clean commercial boundary becomes legally confused. Prevention: clean-room implementation, dependency review, explicit license decision, and no source copying.

## 16.12 We made compatibility profiles executable scripts

A profile ecosystem becomes an unreviewable remote code execution channel. Prevention: closed declarative schema and separately reviewed implementation capabilities.

## 16.13 We used paths as identity

Moving a library or reinstalling a module breaks projects or selects the wrong class. Prevention: exact IDs/digests with paths as mutable locations.

## 16.14 We declared success at first sound

Projects later reopen silent or at defaults. Prevention: project recall is a mandatory early capability, not final polish.

# 17. Prohibited designs

- Loading a Windows DLL directly into the native Linux DAW process.
- A shell script presented as the product architecture.
- A default single global prefix for all vendors.
- A default single Windows process for all plug-ins.
- Automatic use of whatever `wine` or Proton happens to be first on `PATH`.
- Depending on the Steam client or non-Steam-game entries.
- Allowing runtime/profile updates to mutate working environments silently.
- Storing arbitrary executable shell/PowerShell code in compatibility profiles.
- Running installer, network, filesystem, logging, or dynamic allocation work on the audio callback.
- One synchronous request channel that assumes no reentrant callbacks.
- Embedding C++ objects or ABI-unstable types in the Rust boundary.
- Publishing an unknown commercial module to Bitwig before isolated scan/quarantine.
- Treating editor success as processor success or vice versa.
- Treating a screenshot as compatibility proof.
- Capturing credentials or tokens to “help” authorization.
- Patching, bypassing, or emulating vendor licensing.
- Redistributing commercial installers, plug-ins, paid presets, or sample libraries.
- Deleting an environment as the first repair action.
- Rewriting opaque plug-in state to relocate content.
- Claiming all Linux, all Flatpak DAWs, all VST3, all JUCE, or all vendor products from one fixture.
- Selecting a consumer product name that implies format/vendor affiliation without review.

# 18. One bounded next decision

The repository-design seed deliberately selects no implementation slice. The next decision should choose among three bounded starts:

## Alternative A — Serum 2 fixture reconnaissance

Observe the exact lawful installer, authorization channel, module path, content roots, popup/browser behavior, and current experimental-runner behavior on the reference Steam Deck/Bitwig system. No bridge code.

**Strength:** removes the largest product unknown before architecture hardens.  
**Risk:** produces evidence but no code seam.

## Alternative B — native Bitwig VST3 host probe

Build a tiny deterministic Linux VST3 probe that Bitwig Flatpak discovers and instantiates. No Windows process or Serum.

**Strength:** proves toolchain, bundle, sandbox, and host publication cleanly.  
**Risk:** does not pressure the commercial fixture.

## Alternative C — combined Serum factory census vertical

Install Serum manually/experimentally, build Windows scanning plus a mapped native proxy, and make Serum appear by exact class identity in Bitwig without audio.

**Strength:** exciting first cross-boundary proof.  
**Risk:** combines installer, authorization, runner, scanner, VST3 proxy, Flatpak, and proprietary-module uncertainty; a failure will be difficult to assign.

## Technical-lead recommendation

Perform **A and B as two small independent slices, then C becomes a much narrower factory/proxy slice**. Serum 2 remains the first real commercial plug-in throughout. The open reference probe does not replace it; it gives us a controlled instrument for proving the Linux host boundary and later malformed/failure behavior.

The operator should choose the next active slice only after reviewing the initial dossier and current fixture availability.

# 19. Closing product test

The project succeeds when a Linux musician can think:

```text
I own this supported Windows plug-in.
I installed it through one application.
It appears normally in my native DAW.
It sounds and behaves correctly.
My presets and content are where I expect.
My project comes back after a reboot.
An update cannot destroy the working version without a way back.
When something fails, the application tells me whose failure it is.
```

The user may inspect runners, environments, protocol versions, and class IDs—but they should never be forced to learn them merely to make music.
