# K8I1 — Exact Kontakt 8 MSI diversion and verified deployment

## Selected claim

For the exact Native Instruments **Kontakt 8 Player 8.13.1** package, the managed
Native Access session may divert the setup wrapper's one
`MsiInstallProductA`/`MsiInstallProductW` transaction into a source-owned,
package-derived deployment transaction. The wrapper receives success only after every
selected payload byte and every required Native Instruments product-state value has
been committed and independently verified. Any failure rolls back the transaction and
terminates the exact setup generation with Windows error 1603.

This is a Kontakt-specific compatibility adapter. It is not a replacement Windows
Installer, an arbitrary hook facility, or authority for another product or package.

## Components and owners

### Manager

The manager admits the exact package and immutable software generation, creates an
operation/nonce-bound private transaction directory, and projects the fixed K8I1
authority into the renderer specification. Caller input cannot select a hook command,
service, Wine prefix, destination, registry key, package, or product record.

### Renderer session

The existing NAO1 renderer owns Native Access, NTKDaemon, the Kontakt setup, the shim,
the deployment worker, and cleanup inside one renderer unit/cgroup. It installs the
per-application DLL override only for `Kontakt 8 Setup PC.exe`, arms exactly one
private request/result handoff, and restores the prior override and DLL state at
session retirement.

### Windows forwarding shim

A 32-bit source-owned `msi.dll` exports the exact names and ordinals of the pinned
Proton Wine `msi.spec`. Every export except `MsiInstallProductA` and
`MsiInstallProductW` forwards to the patched, exact `msi_lvb_real.dll`. The two selected
exports are authorized for exactly one closed setup/package/operation transaction.
That matching call writes one request and waits for one result for a fixed bound.
Any other invocation of either intercepted A/W export fails this exact setup with
1603; it is not forwarded into the known-broken ordinary MSI execution path.

The shim contains no network client and no general command runner. A failed, malformed,
duplicated, timed-out, or adverse result terminates the exact setup process with 1603.
It never returns success merely because the request was accepted.

### Deployment worker

The source-owned worker accepts exactly one request from the exact setup process
generation. It validates the operation, nonce, request ordinal, package path and hash,
setup identity, renderer cohort, physical prefix, and immutable K8I1 authority before
applying the compiler-produced plan. The exact setup generation remains retained until
its Windows exit and descendant retirement are observed.

The pristine MSI and staged `OFFLINE`/FileBag are layout authority. The rewritten MSI
is observation evidence, not file-layout authority. The plan binds the relevant
`Directory`, `Component`, `File`, `Feature`, `FeatureComponents`, `Registry`,
`InstallExecuteSequence`, `CustomAction`, `CreateFolder`, `RemoveFile`, and `Shortcut`
facts. Service, class, type-library, environment, and the other separately listed
mutation-bearing tables must be empty or absent in this initial adapter. Silent
omission is refusal.

The source-owned package compiler opens the exact pristine MSI through the fixed
Windows table exporter and creates its own fresh IDT projections. It enumerates the
complete `_Tables` roster; every present table receives a machine-readable
disposition. Every selected file is derived through `File -> Component -> Directory
-> FeatureComponents -> Feature`, using the exact normalized properties captured at
the intercepted `MsiInstallProduct` call. Package code and version are derived from the
MSI `Property` table; command-line attempts to replace package identity refuse.
Registry values come from exact `Registry`
rows. Custom actions are joined to `InstallExecuteSequence` with their condition,
type, source, target, and exact row digest. This first adapter explicitly omits those
actions because it owns the selected package deployment; that omission is part of the
reviewed compiler result rather than free-form prose. Selected `RemoveFile` rows and
any action or mutation-bearing table without a source-owned package-specific
disposition are refusal. Caller-supplied plans and caller-supplied table directories
are not accepted. No proprietary table projection or payload is committed to this
repository.

The compiler result has its own digest. Production adapter sealing and renderer
admission are source-disabled until independent review pins that digest, the exact
disposable-prefix proof digest, and the final archive digest. Merely placing an
adapter-shaped archive in a software generation cannot activate K8I1.

## Closed state machine

1. `unarmed`
2. `armed` — exact shim, real MSI library, per-app override, authority and handoff are
   installed for the renderer operation
3. `intercepted` — exactly one exact setup generation submitted one A/W request
4. `planned` — all selected files, destinations, product state, omissions, free space,
   and rollback targets are exact
5. `staged` — every source file was hashed and staged on the destination filesystem
6. `committing`
7. `payload_verified` — selected payload and product state match before the wrapper resumes
8. `shim_success_returned`
9. `setup_terminal` — the exact setup generation has exited with a retained Windows status
10. `post_setup_verified` — payload/state survive wrapper completion and no installer descendant remains
11. `reported`
12. `disarmed`

Every fallible transition has a retained adverse state. `payload_verified` authorizes
only the shim's success return. Installation is not complete until `post_setup_verified`.
Rollback material remains live until that later boundary.

Every required file has exactly one source, one destination, one size, and one SHA-256.
An unresolved or ambiguous source, destination, property, custom action, or required
state value refuses before mutation.

## Transaction and rollback law

Before mutation, the worker verifies every source, available space, destination-root
custody, and an exact rollback manifest. It stages every new file under a private
prefix-owned root on the same filesystem as `drive_c`. Existing destinations are
copied to the rollback root and hashed; absence and any destination-directory creation
are recorded explicitly before either is changed.

Commit uses atomic replacement where the filesystem permits it. Each installed file
is rehashed. Product records and registry values are written from package-derived,
fixed K8I1 data only after file staging succeeds. The worker then reopens and verifies
the standalone and VST3 files and all required state.

Stage, rollback, and journal data live under a private prefix-owned transaction root
on the same filesystem as `drive_c`, verified by device identity. The complete prior
identity and metadata are fsynced before the first replacement; every intended and
completed directory, file, registry, shim-result, and terminal transition is
journaled before it occurs. Recovery is restartable from that journal and requires
proof that the retained setup generation is terminal and its descendants are absent.
On any failure it
restores replaced files and metadata, removes files and values created by this
operation, removes the operation's product record, verifies rollback, retains private
evidence, and returns failure. Adapter disarm and dependency retirement cannot start
while the transaction owner or exact setup observer remains live.

The rollback journal also retains byte and metadata copies of pre-existing files in
the exact Kontakt application, common-engine, VST3, and product-record surfaces. After
the wrapper exits, an added, removed, or changed file in those surfaces is adverse;
rollback restores the recorded surface rather than merely removing the newly selected
payload.

Temporary adapter arming follows the same rule: its prefix-resident journal records
the complete prior DLL/config identity and intended mutation before replacement, marks
each committed replacement only after directory fsync, and supports restartable
disarm. Registry calls share one aggregate transaction deadline; cancellation is
observed during forward work while rollback retains its own bounded completion window.

## Terminal truth

The result keeps these axes independent:

- Native Access application session: `completed | cancelled | failed`
- Kontakt installer transaction: `completed | failed | not_requested`
- Kontakt payload verification: `verified | absent | incomplete | unavailable`
- NI product recognition: `installed | not_installed | unavailable`
- dependency cleanup: `graceful_service_retirement | exact_owned_session_cleanup |
  cleanup_unconfirmed`

Native Access UI text, wrapper exit, zero live processes, an uninstall key, or cleanup
success is never installation authority.

## Required proof

Generated qualification crosses the production manager authority, renderer protocol,
shim, plan validator, transaction, rollback, terminal parsing, and frontend. It
proves exact A/W interception, forwarder completeness, ordinal fidelity, one request,
no arbitrary execution/network import, exact package refusal, complete mapping,
source/destination hash equality, rollback, no false product record, retryability, and
independent result projection.

One disposable-prefix proof is required before managed-prefix use. It uses the exact
retained package and existing runner/session topology. Its typed result must establish
that the real patched forwarding DLL reads the rewritten `_Tables`, `Directory`, and
`File` tables before exactly one interception; that the exact setup exits zero; that
post-wrapper payload/state verification passes; and that Native Access recognizes the
product after refresh and cold reopen, the standalone launches, the VST3 enumerates,
and cleanup completes. Its forced-failure branch must return 1603, roll back every
mutation, leave no payload or product record, and remain retryable.

The managed NI prefix is not mutated until that disposable proof passes and a separate
review authorizes the exact operation. Direct application interaction remains with the
operator.
