# AP11 — Vendor editor implementation and observed limits

**Implementation is available for review; the AP11 outcome is incomplete.** The real FRAGMENTS editor controls the existing bridged instance, survives close/reopen, and saves/recalls a stopped-transport edit. Serum's real editor now renders, but reports that the managed machine is not authorized. No vendor authorization was attempted. Actual Serum preset selection, musical automation recording/playback and editor-edited sound recall are therefore unproved. The detached-window focus request also does not reliably raise an existing window hidden behind Bitwig.

This branch starts at prepared `b8cee7539141ef7b9db615b3fdd1766918b4052a`, based on integrated main `b8c332c2e536e4d9d6103d6d3d0696ffd6369f29`. AP8/#67, AP9/#69 and AP10/#71 source and evidence retain their original claim levels. [Issue #75](https://github.com/kasselvania/Linux-VST-bridge/issues/75) remains open. ## Implementation and ownership

The commercial VST3 controller returns a small native X11 launch/status panel through `createView(kEditor)`. It uses the host's UI run loop and SDK connection-point messages. The Rust backend binds commands and notifications to the existing supervised processing session and its generation. The UI companion mapping has two preallocated 512-message rings, a 552-byte fixed message, and independent close/revision controls. It carries no SDK pointer, opaque preset or vendor window handle across platforms.

The existing Windows controller owner thread pumps Win32 messages and bounded control work while active, stopped and awaiting lifecycle requests. It creates the view from the SAME controller already connected to the audio component, initializes its COM apartment, negotiates Windows platform support, installs a local parent and frame, handles scaling when exposed, sizing constraints, focus and input, and removes/releases the view before destroying its parent and controller. One window belongs to each session. Closing that window or the native panel closes the view without closing the processing instance. Restore and scanning alone do not open it.

Vendor `beginEdit/performEdit/endEdit`, groups, dirty state and supported restart callbacks travel to Bitwig's component handler on the native UI thread. The DSP edit comes back through host `inputParameterChanges`, including zero-frame flushes. The UI route does not make a duplicate processor edit. Host/controller updates reach the actual Windows controller on its owner thread; nested gesture echoes are suppressed. An atomic revision coordinates admitted audio updates, host UI values and vendor edits so older refreshes cannot overwrite newer values. Preset metadata/value refresh uses bounded chunks and real SDK parameter IDs, titles and values.

Saving drains already queued UI edits before the existing state barrier, without waiting for native UI work from that same thread. State capture reads state; actual restore performs component-to-controller synchronization once. The UI queue, window processing and GUI acknowledgement do not sit in the audio delivery path. Overload and unsupported operations are explicit. A close epoch/cutoff remains available when the ordinary UI ring is full and cancels older pending opens. This establishes bridge-side independence; it cannot prevent vendor-internal GUI/DSP contention.

Factory/panel names now use inspected vendor class metadata. Processor/controller UUID derivation, parameter IDs and saved-project binding remain unchanged. Old custom device labels remain visible in existing Bitwig projects. UI protocol/ABI 1 is separate from process protocol minor 10. AP10's mailbox layout and returned event payload ownership remain intact.

## Demonstrated faults and repairs

**State-capture feedback.** The initial stopped Serum load produced 467,379 GUI notifications, no native UI commands and 178 identical state captures. Capture was unnecessarily restoring component state to the controller, causing parameter invalidation and another host capture. Making capture read-only retained the actual restore once. The repaired load stabilized at 5,250 initialization notifications and two post-restore captures. The SDK state regression exercises this production helper. The old session is retained as `4346e409…`.

**View attachment and owner-thread setup.** Four early Serum attachment attempts exited the Windows host with status 5. Scaling was initially performed after setting the frame, permitting a resize callback before attachment; redundant unchanged-size notifications also occurred. SDK tests now cover initial scale/frame order and real versus unchanged sizing. Those repairs alone did not make Serum attach. The Windows owner thread was not COM-initialized; initializing its apartment allowed real attachment. The failed scaling/size attempts remain failures, not independent proof of the final cause. The initial COM query and successful initialization result are retained.

**Native panel input.** A production X11 panel test found that pointer events delivered to the host parent were not selected by the child view. Pointer-grab event handling was corrected. The original failing and repaired CI runs are linked in [tests.json](../evidence/AP11/tests.json).

**FRAGMENTS view removal.** Initially, calling `removed()` from `WM_CLOSE` faulted through Wine dispatch, leaving the view marked as closing. A later close falsely appeared acknowledged. Removal now occurs after dispatch returns; reentrant removal is refused, and focus/size/key callbacks do not reenter a view being removed. Those necessary lifecycle fixes did not cure the commercial fault: it then exited the host with status 5 instead of leaving a stuck view.

A bounded exception snapshot identified access violation `0xc0000005`, RCX=0, at `uiautomationcore.dll` RVA `0x7988`, `create_uia_node_from_elprov+0x18`, dereferencing the provider pointer. Owned mappings and the pinned DLL's symbols/disassembly also resolved RAX to `UiaDisconnectProvider`. No stack was captured, so the exact vendor caller is unproved. [The retained fault record](../evidence/AP11/removal-fault.json) separates the observation from that inference.

With the **same Windows/native binaries and saved sound**, disabling that Windows accessibility DLL for the owned process allowed repeated real view removal, reopening, continuing audio and normal process close. `tools/ap8_preview.py --disable-windows-accessibility` exposes this explicit, default-off option. It preserves other overrides and does not edit the prefix or siblings. The comparison used an equivalent private launcher override with the existing supervisor; the final live check used the delivered CLI option. This disables Windows UI Automation/screen-reader integration, **not VST parameter automation**. It is a bounded workaround, not a general Arturia or Wine repair. Two attempted resource-manifest additions did not fix the resource warning or close fault and were removed again. No vendor or runtime binary was patched.

**False host failure during retirement.** Healthy closes still recorded GUI failure 10. Hosts can disconnect the controller before a final state capture, or disconnect the processor's return connection before the controller sends its close. The bridge now withdraws UI-consumer capabilities before controller retirement and avoids draining to a retired consumer. A successfully delivered close also succeeds when its return connection has already retired; other commands still require the return route before application, and failed delivery is not acknowledged. Both SDK disconnect orders have failing-before/passing-after regressions. After the processor-first repair, the real final FRAGMENTS close changed from failure 10 to 0. This explains that diagnostic, not historical native engine crash #73.

## Editor cost at 512 added frames

The comparison used the same FRAGMENTS instance, saved sound and existing AP10 input clip looping bars 1–3. Rate was 48 kHz, float32; Bitwig callbacks were 256 frames, added bridge delay 512 frames, vendor latency 192 frames (704 reported total). PipeWire quantum 512/minimum 256 remained unchanged.

| Editor condition | Supervised cohort CPU, % of one core | Bitwig UI / audio engine / plug-in host CPU, % | Captured local audio |
| --- | ---: | --- | --- |
| Closed | 84.24 | 27.92 / 9.57 / 8.31 | 12.971 s, nonzero output |
| Open, idle | 102.99 | 24.66 / 10.04 / 8.78 | 12.971 s, nonzero output |
| Active controls | 105.34 | 27.65 / 10.24 / 8.84 | 12.971 s, nonzero output |

The owned cohort includes Python supervision, the Windows host and Wine. These are not Python-only measurements. Each CPU window was approximately 15 seconds; monitor startup shortened the captured audio. Active use consisted of several short drags, not continuous 15-second motion or heavy preset browsing. The idle editor added about 18.75 percentage points of one core; active use added about 21.10 points versus closed. These short sequential samples have no randomized repetitions or uncertainty interval. [Raw comparison metrics and limitations](../evidence/AP11/editor-comparison.json) include levels and process deltas.

The enclosing session delivered 62,875,392 of 62,877,952 frames: **512 priming frames, 2,048 missed/expired frames across five gaps/eight callbacks, no rejected callbacks**, and no lost observation jobs/samples or unretained gap traces. It includes stopped/UI/debugging/automation work outside the three captures. There were no per-condition callback-counter snapshots; only the first gap also has a retained absolute-time Linux request trace. Consequently no per-condition zero-gap claim or causal GUI attribution is established. All eight gap records remain in [the comparison session](../evidence/AP11/fragments-comparison-session.json).

Those records include queue delays around 10.6–12.2 ms, a 12.6-ms reply interval, and one 28-ms send interval followed by queued late requests. They locate delayed stages, not computation-versus-scheduling causality. This AP11 comparison does not explain every AP10 outlier. The later focused stopped-transport lifecycle session had zero recorded gaps over 8,337,408 frames; that is not a replacement musical stress result. No exact reference-error or physical round-trip claim is derived from commercial audio or Moonlight. **512 remains recommended**; no buffer was increased and no matrix was replayed.

## Restored settings and continuation limits

[Cleanup](../evidence/AP11/cleanup.json) confirms all 20 owned sessions retired with positive containment, no owned descendants, and empty process groups. The task owner was stopped and its endpoint removed. Original scanner binaries/markers and historical session files, Bitwig preferences/cache and the original empty publication directory were restored. The 512-frame delay and all observed PipeWire clock settings match the originals. Temporary trace/mailbox override files, two Tahoma files and their two added registry entries, and unsuccessful FRAGMENTS manifest additions were removed. The original Serum renderer setting is restored; authorization data was neither copied back nor modified. Original AP9/AP10 project hashes are unchanged. Private AP11 projects, diagnostics and build receipts remain available on the fixture.

This means the candidate is not left deployed in the user's normal environment. It still requires prepared native artifacts, the existing supervised preview infrastructure and compatible vendor environments. A future Serum continuation needs authorized vendor UI access and the two existing-font registrations to render that dialog/editor in this fixture; new activation remains outside the selected slice. Window-manager focus behavior and the FRAGMENTS resource warning remain open. Actual Serum preset/automation/recall and a matched Serum editor-performance check cannot be claimed from the FRAGMENTS or SDK evidence. Leave the implementation PR unmerged for review.
